xHCI 1.2b §4.23 Power Management · p310–326 · §4.23.1 Power Wells p310 / §4.23.2 xHCI Power Management p311 / §4.23.2.1 Save and Restore Operations p314 / §4.23.3 PCI Power Management p315 / §4.23.4 USB Power Management p315 / §4.23.5 USB Link Power Management p315–326

规范要义

本节把散在规范各处的电源机制收拢成一张总图。xHC 有两口电源井：Core 井（核心逻辑）与 Aux 井（辅助供电，若支持）——Core 井可被系统关断，Aux 井从上电起常在。本页「xHCI 驱动」即规范原文所称 system software（系统软件）。软件要把 xHC 停电再续命，靠一对 USBCMD 控制位：Save State（CSS）与 Restore State（CRS）——寄存器读得走的状态直接存档；寄存器看不见的内部状态（如 ERDP 关联的 Ring Cycle State、已启用的 Device Slots 集合）也必须一起保存恢复，且两旗只在停机态（R/S=‘0’）可置（p311–312）。

井的规则决定「什么会复位、什么能活过断电」：Core 井内存寄存器在 Chip Hardware Reset、HCRST、D3hot→D0 转换时回默认；Aux 井只在初次上电或 HCRST 时复位——PME 唤醒上下文因此能活过 Core 井断电（p310–311）。PCI 侧 D0→D3hot→D3cold 的功耗态迁移（Appendix A，§4.23.3 所指）加上 Save/Restore 两个操作，构成系统挂起→唤醒→恢复的完整主线（本页泳道图）；软件出 D0 前还必须先把全部 Enabled 下游端口置 USB 挂起（p557）。端口级挂起/恢复的时序细节在 §4.15；运行期更浅的链路低功耗态（USB2 L1 / USB3 U1·U2）由 §4.23.5 管理——根集线器端口 LPM 机制（Table 4-12 状态映射）＋ Slot Context Max Exit Latency 调度机制，后者以一个最坏唤醒延迟值供 xHC 对 SS Isoch 提前发 PING 唤链（p324–326）。§4.23.4 本身只做指路：USB2/USB3 细节归各自规范，USB PD 走 ACPI（p315）。

原文对照

“When system software decides to power down the xHC with the intent of resuming operation at a later time, it shall read the xHC registers and save their state.”
停电前的总纲：寄存器状态读出保存，上电回 Run 前全部写回——Save/Restore 这对操作的存在理由。
xHCI 1.2b §4.23.2 p311
“The Save State and Restore State flags may only be set when the xHC is Stopped (Run/Stop (R/S) = ‘0’).”
两旗（CSS/CRS）只在停机态可置——挂起/恢复的入口门槛。
xHCI 1.2b §4.23.2 p312
“Note: The state of a Root Hub port is not covered by a Save or Restore operation.”
根集线器端口不在 Save/Restore 覆盖内——端口与拓扑由软件在恢复时重走（恢复步 9）。
xHCI 1.2b §4.23.2.1 p314 Note
“Note: xHC implementations shall support Link Power Management for all USB protocols that it supports.”
LPM 不是可选项：xHC 支持的每种 USB 协议都必须支持链路电源管理——具体特性看 Supported Protocol Capability（§7.2.2.1.3）。
xHCI 1.2b §4.23.5 p315–316
“It is not practical for the xHC to track the state of every link in the USB topology, so the Max Exit Latency field in the Slot Context identifies the worst case exit latency for the links and hubs between the xHC and the device when scheduling transfers to power managed devices.”
xHC 不逐链路跟踪状态——用 Slot Context 的 Max Exit Latency 一个最坏值兜住整条路径，调度按它留余量。
