xHCI 1.2b §4.13 Device Notifications · p229–232 · §4.13.1 Latency Tolerance Message Handling

规范要义

USB3 规范定义了 Device Notification Transaction Packet（设备通知事务包）：16 种通知类型里，一部分由 xHC 直接处理，另一些可以上报软件。DNCTRL（Device Notification Control）寄存器让软件逐位选中自己关心的通知类型——被选中的类型会生成 Device Notification Event 写入事件环（TRB 格式 §6.4.2.7）。

事件的去向由设备槽决定：xHC 用该槽 Slot Context 的 Interrupter Target 字段选择接收它的事件环。调试例外：DNCTRL 也允许把本来由 xHC 直接处理的通知类型一并上报（便于排查）。

本节主体 4.13.1 是 LTM（Latency Tolerance Messaging，延迟容忍消息）：USB3 设备用 LTM TP 报告自己的延迟容忍值（BELT）；xHC 逐设备记录 Device BELT，比较后把最小值经宿主平台的 LTR 机制转发——这条转发路径在三方泳道之外（平台总线特定，如 PCIe LTR）。软件可用 Set LTV 命令自设一个 Device BELT 值（§4.6.14）。

📎 §4.13 DNCTRL 按位选通知类型（p229）

xHCI 1.2b §4.13 · p229

The Device Notification Control (DNCTRL) register allows system software to individually select which notifications are important to it and shall generate a Device Notification Event.

16 类通知逐位选——选中的才生成事件；调试例外（同页 Note）：xHC 自处理的类型也可打开上报。

📎 §4.13 事件路由跟着槽走（p229）

xHCI 1.2b §4.13 · p229

The xHC shall use the Device Slot’s Slot Context Interrupter Target field to determine the Event Ring that shall receive the event.

DN 事件进哪条事件环由该槽 Slot Context 的 Interrupter Target 字段决定——不是固定进 0 号中断器。

📎 §4.13.2 收 FUNCTION_WAKE 应置 N1（p231）

xHCI 1.2b §4.13.2 · p231

Software should set flag N1 in the DNCTRL register to enable the generation of Device Notification Events when FUNCTION_WAKE Device Notifications are received.

规范对软件的应然：想收功能唤醒通知就置 N1。基线内核 xhci 驱动自身不写 DNCTRL（全树无写入点）——如实注记：本链场景的 N1=1 来自平台固件/调试路径。

📎 §4.13.2 FUNCTION_WAKE=功能级远程唤醒（p231）

xHCI 1.2b §4.13.2 · p231

A USB3 device sends a FUNCTION_WAKE Device Notification Transaction Packet to inform the host of a “Function Remote Wake”.

Function Remote Wake（功能级）与底层 USB 信号发起的 Remote Wake（链路级）是两回事（同节 Note）——前者走通知包，后者只是链路信号。

📎 §6.4.2.7 DN Event TRB 报告收到的通知包（p446）

xHCI 1.2b §6.4.2.7 · p446

A Device Notification Event TRB is used to report the information received in USB Device Notification (DEV_NOTIFICATION) Transaction Packets from USB Devices.

事件字段=通知包的转写：Notification Type（7:4 位）＋Device Notification Data（63:8 位，DNTP 05h-0Bh）＋Slot ID（31:24 位）。

📎 §6.4.2.7 完成码恒为 Success（p447）

xHCI 1.2b §6.4.2.7 · p447

Completion Code. This field encodes the completion status of the TRB, and shall always be set to Success.

DN 事件没有失败语义——它报告的是「收到了通知包」这件事本身。

📎 §4.13.1 LTM 由 xHC 自处理（p231）

xHCI 1.2b §4.13.1 · p231

The xHC hardware automatically handles LATENCY_TOLERANCE_MESSAGE Device Notifications (Notification Type = 2) so there is no need to enable Device Notification Event generation for this notification type.

LTM（Type=2）在 xHC 内消化（收 BELT→比较→经平台 LTR 转发）——不需要也不应该为它开事件生成。

📎 §5.4.4 复位后通知全关（p365）

xHCI 1.2b §5.4.4 · p365

If a flag is set for a specific notification type, a Device Notification Event shall be generated when the respective notification packet is received. After reset all notifications are disabled.

DNCTRL 复位值 0000 0000h——16 类通知默认全关；不置位就永远收不到 DN 事件。

📎 §5.4.4 16 类里只有 FUNCTION_WAKE 该上报（p366）

xHCI 1.2b §5.4.4 · p366

Of the currently defined USB3 Device Notification Types, only the FUNCTION_WAKE type should not be handled automatically by the xHC.

同页 Note：除调试外软件只该往 DNCTRL 写 0002h（只开 N1）——常规上报的常客只有功能唤醒一类。
