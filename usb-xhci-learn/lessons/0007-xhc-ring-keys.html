钻点一 · cycle bit：环的生产/消费合同

环形缓冲没有"空/满"标志位——软件与 xHC 是两个独立时钟域的写者/读者，xHCI 的立法答案是 cycle bit（TRB 控制字段 bit0，§4.11.1 TRB Template）：每个环有当前轮次（0 或 1），生产者填好 TRB 数据后把 cycle 置成当前轮次=发布；消费者只取 cycle 匹配的 TRB；写者追上读者一圈后轮次翻转，旧 TRB 的 cycle 自然失效。三种环的角色分工内核注释一句话说尽：

xhci-ring.c:276 注释原文："See Cycle bit rules. SW is the consumer for the event ring only."——传输环/命令环：软件生产、xHC 消费；事件环：xHC 生产、软件消费。生产/消费两侧各有一套翻转逻辑。

cycle 这把钥匙先单独转一圈——三帧只看 cyc 与轮次的比对（其余三把钥匙全部静音：每颗 TD 只有 1 颗 TRB、不跨缝、不谈 chain 细节；无 JS 时全部帧定格可读）：

第 1 帧"空"＝cyc 不匹配——环上没有任何标志位

本帧只看槽0：cyc=0，两侧轮次都是 1——不匹配。xHC 顺序扫描，停在第一个不匹配处（§4.9.2）：这就是"空"。环形缓冲没有任何"空/满"标志位，"空"是读出来的，不是标出来的。

第 2 帧发布＝把 cyc 写成当前轮次；消费＝校验通过后取走

本帧只看槽0 的 cyc=1 是怎么来的：软件先把数据写进 DW0-2，wmb() 之后才把 DW3 的 cyc 写成 1（＝当前轮次）——这一写就是"发布"。敲门铃，xHC 校验 cyc==自己轮次 → 取走。注意"绿"不是槽的属性，是"cyc 与轮次比对通过"这一事件的状态；消费后槽里 cyc=1 原样留着（残影），没人去擦。

第 3 帧第 2 圈：同一个槽，靠另一个 cyc 值再绿一次（N 颗 TD 已略）

本帧只看槽0 的两段历史：上一圈它靠 cyc=1 绿过（那个 1 现在还留在槽里，成了旧轮残影）；这一圈软件重写 cyc=0，它又绿了。同一个槽、两种"绿"——"有效"从来不是槽的属性，是"cyc 是否等于当前轮次"的比对结果。旧残影 cyc=1 在轮次 0 下自动作废，谁也不用去擦：这就是无锁环形缓冲从不需要"擦除"的全部秘密。

一句话收拢：cycle bit 是无锁环形缓冲的空满合同——数据先落、cycle 后翻（wmb 保证）；谁生产谁翻转发布，谁消费谁校验匹配；跨圈由 Toggle Cycle 位让双方轮次同步翻转。

钻点二 · Link TRB 与回绕：事件环为什么没有

传输环 / 命令环事件环（§4.9.4）

回绕机制xHC 扫到 Link TRB，跳指针、按需翻轮次xHC 写到段尾（地址=基址+（大小−1）×16）即回下一段/首段；软件侧 inc_deq 用 last_trb_on_seg/last_trb_on_ring 判段尾（:191-198）

为什么事件环不需要 Link TRB？两颗环对"接缝几何"的登记地点不同：传输环在数据流里自描述——xHC 扫描时只认 TRB，"下一颗去哪"只能写进流内，Link 亲自占末槽报路；事件环登记在环外，登记链三级：① 寄存器（每颗事件环一组，§5.5.2.3，p425-428）——ERSTSZ 登记共几段、ERSTBA 登记段表本身放在内存哪个地址、ERDP 登记软件消费到哪（xHC 据此回收槽位；软件写它必须"前进"，见上表末行）；② ERST 段表（Event Ring Segment Table，§6.5/Table 6-95，p514-515）——放在系统内存里的条目数组，每条 16 字节＝8 字节段基址（64B 对齐）＋2 字节段大小（段内 TRB 颗数，合法域 16–4096；第 3 帧图里的"大小 8"是画图取小）；③ 段行走（§4.9.4，p179）——xHC 从第 1 段首槽起逐颗写事件，段尾＝基址＋（大小−1）×16——纯算术算出，不读任何 TRB 内容就知道该跳；到段尾翻表的下一条跳下一段基址，最后一条读完绕回第 1 段（初始化序＝写 ERSTSZ→ERDP→ERSTBA，ERSTBA 写下即启动事件环，§4.2）。所以事件环里每一颗槽都是有效载荷，没有一颗要为"报路"牺牲——接缝住在寄存器与表里，不住在环里。两套方案解决同一个问题：环没有尽头，回绕点必须在可靠的地方被声明。实现≠规范 内核对特定厂商硬件还有一个规范没有的防御：ETRON 主控上若 Setup/Data 段恰好跨 Link TRB 会被打断，驱动主动垫一个 No-Op TRB 避开接缝（queue_ctrl_tx 头部 quirk 分支，xhci-ring.c:3775 起）——评审 quirk 补丁时先问"它防的是哪家硬件的什么行为"。

接缝也单独量一遍——三帧只看"直线怎么变成圆"与"缝的两种缝法"（cycle/chain 全部静音）：

第 1 帧内存里的真实形态：环就是一条直线

本帧只看"圆"的真相：内存里没有圆。xHC 走到段末 0x1070 再 +16 就踏出这段了——没有任何自然机制把它送回 0x1000。"环形"是一个需要被造出来的假象，接缝就是造这个假象的地方。

第 2 帧接缝＝末槽→首槽的那一刀；Link TRB 就是接缝上的路标
指针：下一槽地址（单段环指回首槽，多段环指向下一段首槽） ② 控制字 bit1＝TC（Toggle Cycle）：过缝翻轮次的指令 ③ 自己的 cyc 位：这条缝本轮的通行凭证　　④ chain 位：TD 跨缝时的续链胶水

本帧只看段末槽：这颗槽住不得数据 TRB。回看第 1 帧底注——xHC 取指就是"读内存、地址每次 +16"：读完一颗，指针落在下一颗，再按那颗 DW3 的 type 字段判断"这是什么、该怎么处理"（type＝每颗 TRB 自带的操作码，正常情况下轮子本来就是靠它分发的）。数据 TRB 的操作码只说"搬这坨数据"，不携带"下一颗去哪"——若末槽放数据 TRB，xHC 读完它，指针 +16 就踏出段外，把环外不相干的内存当作下一颗 TRB 解析、按其中的 type 照常分发执行；那里没人保证是合法 TRB，行为彻底失控。所以末槽固定住 Link TRB：type＝Link 本身就是一条"跳转"操作码——把指针改写成 DW0-1 里的地址，安全送回首槽，Link 就是接缝的实体。四件行李正好是另外三把钥匙的家：指针管"跳去哪"，TC 管过缝翻不翻轮次，自身 cyc 管这条缝本轮通不通，chain 管 TD 跨缝时绳断没断。

第 3 帧同一条缝，两种缝法：传输环缝在流里，事件环缝在表里

本帧只看两个"末槽"的差别：同样要"缝"，传输环把缝写进数据流（Link 自描述）；事件环把缝写在流外面的表里（ERST：基址＋大小）。两套方案解决同一个问题——环没有尽头，接缝处不能被当成普通 TRB 误解。这也回答了钻点二开头的问题：事件环为什么没有 Link TRB——它的回绕不住在环里，登记在寄存器与 ERST 段表中（三级登记链见钻点二开头）。

联动动画 · 四把钥匙拧一圈：cycle bit × toggle cycle × chain bit × Link TRB

四把钥匙里 cycle 与 Link 在本课钻点一、二各自独舞过；chain 与 TC 的独舞在上一课（0006 的三层语法与环几何两节）——现在让四把钥匙在同一颗环上咬合转动。先把四者的分工与关系钉成一张表（这张表就是整个动画的说明书，四个"住在哪"一列看完就知道它们谁也不碰谁）：

钥匙住在哪谁写谁读/执行节奏
cycle bit
（DW3 bit0）		每一颗 TRB生产者发布时写消费者取指时校验每颗 TRB 一次
toggle cycle
（Link 的 DW3 bit1）		只在整环最后一段的 Link TRB建环/扩容时定死跨缝的双方各自执行翻转每圈一次（只在接缝）
chain bit
（DW3 bit4）		能串件的数据 TRB（bulk/int/isoc）；TD 跨缝时 Link 也被改写挂上。控制传输没有这把钥匙（见表下注）排 TD 的软件写xHC 沿链续读每个 TD 边界一次
Link TRB
（整颗 16B）		每段末槽（＝接缝）建环写死＋跨缝改写xHC 跳转依据每段一颗

第四把钥匙不是人人都有：chain 只装在"能被串进同一件"的 TRB 类型上——bulk/interrupt/isoc 的数据 TRB（本动画全是 bulk），加上 TD 跨缝时被软件改写挂绳的 Link TRB；控制传输没有这把钥匙——Setup 段 DW3 bit4:1＝RsvdZ，无位可设（Table 6-26）；Data/Status 段虽有 CH 位，内核控制路径全程写 0，分件由三段类型语法自己扛（TRT 预告＋Status 收口）——完整立法与键盘枚举实弹见本课钻点四。

本帧只看槽0：cyc=0 ≠ 两侧轮次 1——这就是"空"（钻点一独舞第 1 帧同款）。空环不需要任何标志槽：槽0 cyc=0，与两侧轮次 1 都不匹配，xHC 顺序扫描停在第一个不匹配处（§4.9.2）——不匹配=空。软件侧 cycle_state 初值 1；硬件侧轮次由端点上下文 tr_dequeue 的 DCS 位（Dequeue Cycle State）随游标一起种成 1（Initialize Endpoint 时写入）。生产/消费合同从第一颗 TRB 之前就已经成立。

第 7 帧追平收官——同一颗环，第二轮

本帧只看两枚轮次盒＝0：物理上同一颗环，逻辑上已是第二轮。dequeue 追平 enqueue（同停槽2），环再度为空——但两侧轮次已是 0：物理上同一颗环，逻辑上第二轮。槽0/1 残影的 cyc=0 恰等于当前轮次，看着"有效"——但游标永不回头：环空=xHC 停在第一个不匹配处，假绿的残影永远不会被回头看第二眼。合同不靠擦除、不靠标志位，只靠"轮次+单向扫描"。四把钥匙收拢：cycle=每颗 TRB 的锁（当前轮次=有效）、toggle cycle=翻圈凭证（TC 只挂 last_seg 段尾）、chain=捆绑绳（TRB→TD 的边界）、Link TRB=接缝本身＋对表指令——生产者与消费者各执同一套规则的两半。

一句话收拢：cycle bit 是"每颗 TRB 的所有权"——生产者发布时置成当前轮次，消费者取指时对自己的轮次校验；toggle cycle 让两侧在接缝处（且只在接缝处）同时翻圈，chain bit 把可串件的数据 TRB 捆成 TD 并声明边界（控制传输无此钥匙——件界写在类型语法里，见钻点四），Link TRB 身兼指针/TC/自身 cyc/chain 四重身份——四把钥匙咬合，这颗无锁的环才从来不必说出"空"或"满"。生产/消费两侧的动作对照：软件 giveback_first_trb（发布翻 cycle）↔ xHC 取指校验；软件 inc_enq_past_link（跨缝翻轮次）↔ xHC 按 TC 翻轮次；事件环上两套动作整个对调。

这句提问里藏着一次钥匙串门：括号里那条「除最后一颗外都相同」其实是 chain 的规则（TD 内除尾 TRB 外 chain=1、尾 chain=0——0006 的钉死句是「边界＝chain 0」），被记到了 cycle 头上。于是前提看起来全对：同圈内 TD 的 cycle 确实全都相同——但「分件」从来不是 cycle 的工作，就像责怪体重秤量不出身高：它不是干这个的。下面四帧让 cycle 与 chain 第一次同框对照（此前只有独舞与四钥匙齐转，缺的正是并排的这一帧）。布景、货、色板与联动节完全同一套——还是那三颗 130KB 的 bulk 货：

第 1 帧同圈的邻居——假悖论定格：六颗 TRB 的 cyc 全部相同

本帧只看槽2 与槽3 这对邻居：TD1 与 TD2 同圈相邻，六颗 TRB 的 cyc 全部＝1，两件之间连一颗空槽都没有隔开——「cycle 全同 ⇒ 分不出 TD」的前提此刻完全成立。它不是环的缺陷：cycle 从没领过「分件」的任务（下一帧看真正管分件的章）。顺带把假悖论的来路钉死：把 chain 的规则（除尾 TRB 外都相同）背到 cycle 头上，两把钥匙在这一帧确实长得像。

第 3 帧反证：跨缝的一件货，身上同时盖着两个圈的章

本帧只看一件货身上的两种圈号：TD3 发布后（槽6 翻成 1），同一件里首 TRB 属缝前的圈、trailing 属缝后的圈（联动第 5 帧排队中途那次轮次翻转的遗产）。若 cycle 真是件界机制，同一件内圈号就不该中途变——它偏偏只在「过缝」时变，与件边界毫无对齐关系；反过来说，「TD 内 cycle 恒相同」连不变量都不是（跨缝即破）。这是比职责表更硬的反证：cycle 不可能承担分件。另一枚方向性证据：cycle 全环唯一的「反常」在首 TRB（发布前反极性压着，联动第 2 帧），不在收口的尾——若它管分件，例外该出现在边界处才对。

本帧只看「为什么 1 bit 够用」：贴单员永远不会领先取件员一整圈——每贴一批前 prepare_ring 先数余量（xhci_num_trbs_free），不够先扩容（命令环禁扩、直接拒绝；贴码）。于是任一时刻货架上至多两代单（上一圈残影＋本圈新单），奇偶两态判别足矣：把两侧各自维护的「圈计数器」压进内存，只剩末位可写——这就是 cycle_state＝计数器 mod 2；过缝时 TC 让两侧各自 +1（联动第 5/6 帧那次翻转），高位谁也不需要看见。环形缓冲最经典的「游标追平＝空还是有货」难题，xHCI 的答卷：1 bit 数据＋1 bit 进位指令——不用计数器、不用标志位、不用锁。

问二收拢：TD 回答「这件货怎么执行、何时算完成」；cycle/TC 回答上游的货架问题——固定格子的环形货架上「空还是有新货」如何无锁分辨。三个约束（格子不撕单 / 两时钟域无锁 / 唯一通道是内存）把答案逼成唯一形状：新旧写进每张单（DW3 bit0 轮次贴纸）＋过缝进位（TC）。翻圈不是给 TD 用的，是给货架用的。

离场即破的提醒：bulk 传输一个 TD 串几十颗 TRB 是常态——chain 剪刀的主场（钻点三）。正确说法是：规范按阶段记件；控制传输的每件通常恰一颗 TRB（Setup 恒如此、Data 在 Linux 恒如此）；内核再把这几件打成自己的一件对账。这也再次解释问三的立法：这 2-3 件 TD 之间没有 chain 胶水——件界写在类型语法里。

「只是拿个描述符，两颗不就够了吗？」——不够，四条理由：

① TRB 是议程行，不是数据本身。Data TRB 回答「搬什么、搬多少」；Status TRB 回答「怎么办结」——它长度 0、不带一个字节的货，却必须占一行议程，xHC 才有动作可演（发 OUT 零长包、收 ACK）。两颗 TRB＝议程只排到第二幕。
↓
② 三幕是 USB 总线协议的法定结构（USB 2.0 §8.5）——xHCI §4.11.2.2 只是把三阶段 1:1 翻成三种 TRB，内核不是多要一颗、是照单排班：排 Status 那行的注释自己引着规范（:3904）"see Table 7 and sections 4.11.2.2 and 6.4.1.2.3"。
↓
③ 最后一包数据 ≠ 交易完成。短包票（CC=13，残量 46）只是中途报账——记下实际长度 18，但不放行 urb；IOC 只许设在 Status（§6.4.1.2 Note p468＝内核 :3915）——完成中断的定义权本来就在第三幕。
↓
④ 设备要「关门」信号，「成了」这句话只有这幕能说。搬完货设备 EP0 状态机悬在「等主机签收」，OUT 零长包就是主机的回执；STALL 拒绝可以早到 Data 幕，但成功宣言只能晚到 Status 幕。SET_CONFIGURATION 更极端：没有 Data 幕（2 颗的一生，帧 5），Status 的 IN 零长包＝设备「配置已生效」的唯一一句。

反证：真只排两颗——xHC 控制序列停在半空（类型语法没等到 Status 收口），完成事件出不来，设备悬在 Data 幕尾；下一个 setup 能强行重开，但协议管那叫中止上一笔，不叫完成。旁证你已经见过（帧 1 侧注）：SET_ADDRESS 连 EP0 环都不上——走命令环的 Address Device 命令，xHC 自己在线上把三幕演完。同一个道理换个舞台：线上三幕逃不掉，议程写在哪个环上可以换。

问四问五收拢：TD 是两本账——规范按阶段记 2-3 件（Setup 恒单颗是法条、Data 在 Linux 恒单颗是选择），内核按 URB 记 1 件、票根指 Status；三幕是「问 → 答 → 签收」——令牌恒主机发、载荷生产者每幕换手两次，签收不是第三种数据，是「办结」动作本身，软件侧一切「完成」信号（IOC、事件、中断、回调）都记在签收那颗 TRB 名下。方向口诀：Status 恒与 Data 反向（:3904-3909 的 if/else 在翻的就是它）；零数据段控制写则 Status＝IN。
