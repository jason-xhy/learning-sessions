SSPLIT 与 CSPLIT 之间
TT 缓冲与重试的规则

代码基线：/Volumes/KernelSrc/linux · master@62f4c998b297（v7.3-rc4-75，2026-09-23）——规范锚点：USB2 §11.17/§11.18/§11.20/§5.3.2

整体定位（先挂图）

本课钻进 课 0004 ⑥层 TT 的内部，打你测评错的两题：缓冲为什么要两个（Q2）与重试权属在谁（Q3）。两题同源：split 把一次搬运拆成时间上解耦的两段，规则全是围绕这个解耦设计的。

时间解耦：SSPLIT 和 CSPLIT 之间隔着一个真实事务

HS 微帧 125 µs；FS 侧一次满载 64 字节 bulk 事务，光数据就要 64×8÷12Mb/s ≈ 43 µs，加协议开销轻松跨过微帧边界。于是 SSPLIT（交付）与 CSPLIT（取结果）必然是两个不同微帧里的独立事务——中间夹着 hub ↔ FS 设备的真实异步执行：

规则一 · 缓冲（Q2）：双缓冲乒乓与四种握手语义

§11.17/§11.17.4：每个 TT 的非周期方向（bulk/control）至少 2 个事务缓冲。配套的握手语义表（§11.17.1）——每条都有明确含义：

场景hub 回应err_count
TT 无空间接新 SSPLITNAK（空转但不罚）不增
该端点已有 pending/ready 结果ACK 但忽略数据不增
CSPLIT 到但事务还没跑完NYET（下个微帧再来）不增
CSPLIT 到但找不到匹配缓冲STALL（协议违例）按错误处理

另外每端点任一时刻只允许 1 个缓冲结果（Compare_buffs 规则，§11.17.1）——双缓冲是"在飞＋接新"，不是"堆两个结果"。

规则二 · 重试权属（Q3）：三层对照，谁的地盘听谁的

TT 本地（FS handler）——只限非周期的事务错误：bulk/control 在 FS 域遭遇传输错误（bit 错/超时）可本地重试，3 次后以 stall 状态回报；但对 ACK/NAK/STALL 等握手结果不得重试（§11.17.2）。 
/* 摘要库 §11.17.2 引文 */
"If the transaction experiences a transaction error three times,
 the full-/low-speed handler will reflect this as a stall status result"
↓
主机侧——three strikes 与 halt：err_count < 3 主机重试；≥ 3 做端点 halt；halt 之后软件发 Clear_TT_Buffer 清 TT 的 busy 缓冲（§11.17.1/§11.17.5）——这正是 hub_clear_tt_buffer（hub.c:816-831）存在的理由，课 0004 的内核锚点在这里接上规范。 
/* 摘要库 §11.17.1 引文 */
"it increments an error count (err_count) and, if the count is less
 than three..., it will retry the transaction. If the err_count is
 greater or equal to three..., the host controller does endpoint
 halt processing"
↓
periodic（interrupt/iso）——TT 完全不本地重试：§11.20 明文。因为 interrupt 活在主机的微帧管道里（§11.18.4：SSPLIT/CSPLIT 在哪个微帧都排得死死的），NAK 不是错误而是"没就绪"的合法状态（§5.3.2），hub 若自作主张重试会（a）吃掉 187.5 字节/微帧的 FS 预算（b）打乱主机按 bInterval 的服务记账（c）重复执行风险。结果如实经 CSPLIT 回报，何时再试由主机按服务节奏决定；periodic 的 CSPLIT 遇传输错误也是主机侧"立即重试"（§11.18.4⑥），不是 TT 的活。
一句话收拢两道错题：Q2——解耦需要排队，双缓冲=一个在飞一个接新；Q3——重试决策权跟着调度权走：非周期事务错误归 TT（3 次封顶），握手结果与全部 periodic 归主机。
