整体定位（零件已认完，本课让环转起来）

上一课（0006 先认零件）把静态面钉死：TRB 16 字节的每个字段（DW0-1 四种身份、DW2 长度与剩余包数、DW3 控制位）、槽→TD→段→环的组织、切分语法与扩容几何——零件都在桌上，但环还没转。本课收窄为环机制课：只讲环自己怎么转。主角三个：cycle 合同（谁拥有哪颗槽——环形缓冲不用"空/满"标志位的立法答案）、接缝（内存里的直线怎么闭合成圆）、四把钥匙联动（cycle × toggle cycle × chain × Link 在同一颗环上咬合）；收官两章接住 2026-10-09 三课上线当天读者的两个真实追问（分件的是哪把钥匙？为什么非要翻圈？），把四把钥匙的分工逼到墙角再钉一遍。全部动画统一三视角泳道——软件（驱动）｜xHC 控制器｜设备固件，线上通道画在 xHC 与设备之间；一场完整传输的三视角剧（urb→ring 五层包裹、键盘枚举、Data 段生产者与事件通知链、TD 两本账）在姊妹课 0009 一场传输的三视角剧开演。术语约定：本课 TD 默认指规范 TD（§4.9.1：一串 TRB 构成的一件传输）；内核 struct xhci_td 的记账粒度不同——两本账的对照 0009 挑明。

立法（全课通用）：环对设备不可见——环住在只有软件与 xHC 能读写的共享内存里，设备只看得见线上。传输环、命令环、事件环、ERST 段表全住在主存里，门铃寄存器住在 MMIO 里；设备固件的世界观里只有令牌（token）、数据包与握手。本课每部动画的设备泳道都按这条立法画：环上独角戏的帧，设备泳道是「盲区声明」固定框（灰底）；有线上戏份的帧（第 3 章 bulk IN 联动），设备泳道画同期线上活动与 DMA 直写。

第 1 章 · cycle 位：环的生产/消费合同

环形缓冲没有"空/满"标志位——软件与 xHC 是两个独立时钟域的写者/读者，xHCI 的立法答案是 cycle bit（TRB 控制字段 bit0，§4.11.1 TRB Template）：每个环有当前轮次（0 或 1），生产者填好 TRB 数据后把 cycle 置成当前轮次=发布；消费者只取 cycle 匹配的 TRB；写者追上读者一圈后轮次翻转，旧 TRB 的 cycle 自然失效。三种环的角色分工内核注释一句话说尽：

xhci-ring.c:276 注释原文："See Cycle bit rules. SW is the consumer for the event ring only."——传输环/命令环：软件生产、xHC 消费；事件环：xHC 生产、软件消费。生产/消费两侧各有一套翻转逻辑。

生产者侧的翻转带着一道写屏障——先把 TRB 数据写完，再动 cycle，顺序不可颠倒：

生产者：跨段时翻 Link TRB + 轮次取反（传输环，软件是生产者）：

		/* Toggle the cycle bit after the last ring segment. */

cycle 这把钥匙先单独转一圈——三帧只看 cyc 与轮次的比对（其余三把钥匙全部静音：每颗 TD 只有 1 颗 TRB、不跨缝、不谈 chain 细节；无 JS 时全部帧定格可读）：

第 1 帧"空"＝cyc 不匹配——环上没有任何标志位

本帧只看槽0：cyc=0，两侧轮次都是 1——不匹配。xHC 顺序扫描，停在第一个不匹配处（§4.9.2）：这就是"空"。环形缓冲没有任何"空/满"标志位，"空"是读出来的，不是标出来的。

第 2 帧发布＝把 cyc 写成当前轮次；消费＝校验通过后取走

本帧只看槽0 的 cyc=1 是怎么来的：软件先把数据写进 DW0-2，wmb() 之后才把 DW3 的 cyc 写成 1（＝当前轮次）——这一写就是"发布"。敲门铃，xHC 校验 cyc==自己轮次 → 取走。注意"绿"不是槽的属性，是"cyc 与轮次比对通过"这一事件的状态；消费后槽里 cyc=1 原样留着（残影），没人去擦。

第 3 帧第 2 圈：同一个槽，靠另一个 cyc 值再绿一次（N 颗 TD 已略）

本帧只看槽0 的两段历史：上一圈它靠 cyc=1 绿过（那个 1 现在还留在槽里，成了旧轮残影）；这一圈软件重写 cyc=0，它又绿了。同一个槽、两种"绿"——"有效"从来不是槽的属性，是"cyc 是否等于当前轮次"的比对结果。旧残影 cyc=1 在轮次 0 下自动作废，谁也不用去擦：这就是无锁环形缓冲从不需要"擦除"的全部秘密。

一句话收拢：cycle bit 是无锁环形缓冲的空满合同——数据先落、cycle 后翻（wmb 保证）；谁生产谁翻转发布，谁消费谁校验匹配；跨圈由 Toggle Cycle 位让双方轮次同步翻转。

第 2 章 · Link TRB 与回绕：事件环为什么没有

传输环 / 命令环事件环（§4.9.4）
段尾标记Link TRB（§4.11.5，Fig 4-15）——下一槽指针+Toggle Cycle+Chain无 Link TRB——段的范围由 ERST 段表（§6.5）的"基址+大小"声明
回绕机制xHC 扫到 Link TRB，跳指针、按需翻轮次xHC 写到段尾（地址=基址+（大小−1）×16）即回下一段/首段；软件侧 inc_deq 用 last_trb_on_seg/last_trb_on_ring 判段尾（:191-198）
多段衔接Link TRB 链成环ERST 条目数组顺序衔接（Event Ring Segment Table，Table 6-95）
游标寄存器命令环 CRCR（§5.x，RsvdP 位防软件偷写）ERDP（软件消费到哪，§4.9.4：软件写 ERDP 必须"前进"，xhci-ring.c:3026 注释原引）

为什么事件环不需要 Link TRB？两颗环对"接缝几何"的登记地点不同：传输环在数据流里自描述——xHC 扫描时只认 TRB，"下一颗去哪"只能写进流内，Link 亲自占末槽报路；事件环登记在环外，登记链三级：① 寄存器（每颗事件环一组，§5.5.2.3，p425-428）——ERSTSZ 登记共几段、ERSTBA 登记段表本身放在内存哪个地址、ERDP 登记软件消费到哪（xHC 据此回收槽位；软件写它必须"前进"，见上表末行）；② ERST 段表（Event Ring Segment Table，§6.5/Table 6-95，p514-515）——放在系统内存里的条目数组，每条 16 字节＝8 字节段基址（64B 对齐）＋2 字节段大小（段内 TRB 颗数，合法域 16–4096；第 3 帧图里的"大小 8"是画图取小）；③ 段行走（§4.9.4，p179）——xHC 从第 1 段首槽起逐颗写事件，段尾＝基址＋（大小−1）×16——纯算术算出，不读任何 TRB 内容就知道该跳；到段尾翻表的下一条跳下一段基址，最后一条读完绕回第 1 段（初始化序＝写 ERSTSZ→ERDP→ERSTBA，ERSTBA 写下即启动事件环，§4.2）。所以事件环里每一颗槽都是有效载荷，没有一颗要为"报路"牺牲——接缝住在寄存器与表里，不住在环里。两套方案解决同一个问题：环没有尽头，回绕点必须在可靠的地方被声明。实现≠规范 内核对特定厂商硬件还有一个规范没有的防御：ETRON 主控上若 Setup/Data 段恰好跨 Link TRB 会被打断，驱动主动垫一个 No-Op TRB 避开接缝（queue_ctrl_tx 头部 quirk 分支，xhci-ring.c:3775 起）——评审 quirk 补丁时先问"它防的是哪家硬件的什么行为"。

接缝也单独量一遍——三帧只看"直线怎么变成圆"与"缝的两种缝法"（cycle/chain 全部静音）：

第 1 帧内存里的真实形态：环就是一条直线

本帧只看"圆"的真相：内存里没有圆。xHC 走到段末 0x1070 再 +16 就踏出这段了——没有任何自然机制把它送回 0x1000。"环形"是一个需要被造出来的假象，接缝就是造这个假象的地方。

第 2 帧走完末槽跳回首槽——这一跳就是接缝；Link TRB 是接缝上的路标
指针：下一槽地址（单段环指回首槽，多段环指向下一段首槽） ② 控制字 bit1＝TC（Toggle Cycle）：过缝翻轮次的指令 ③ 自己的 cyc 位：这条缝本轮的通行凭证　　④ chain 位：TD 跨缝时的续链胶水 软件（驱动） Link 的写者：建环时写死指针/TC/自身 cyc；排 TD 跨缝时改写 chain（:277-280） xHC 控制器 Link 的读者：type＝Link 即跳转指针、按 TC 翻轮次、按 chain 续链 USB 线（此幕静默——接缝住在内存里，不上线） 设备固件 此幕设备无戏份——环上的事只发生在软件与 xHC 之间，设备只看得见线上。 接缝与四件行李全在共享内存里——设备只等线上令牌

本帧只看段末槽：这颗槽住不得数据 TRB。回看第 1 帧底注——xHC 取指就是"读内存、地址每次 +16"：读完一颗，指针落在下一颗，再按那颗 DW3 的 type 字段判断"这是什么、该怎么处理"（type＝每颗 TRB 自带的操作码，正常情况下轮子本来就是靠它分发的）。数据 TRB 的操作码只说"搬这坨数据"，不携带"下一颗去哪"——若末槽放数据 TRB，xHC 读完它，指针 +16 就踏出段外，把环外不相干的内存当作下一颗 TRB 解析、按其中的 type 照常分发执行；那里没人保证是合法 TRB，行为彻底失控。所以末槽固定住 Link TRB：type＝Link 本身就是一条"跳转"操作码——把指针改写成 DW0-1 里的地址，安全送回首槽，Link 就是接缝的实体。四件行李正好是另外三把钥匙的家：指针管"跳去哪"，TC 管过缝翻不翻轮次，自身 cyc 管这条缝本轮通不通，chain 管 TD 跨缝时绳断没断。

第 3 帧同一条缝，两种缝法：传输环缝在流里，事件环缝在表里

本帧只看两个"末槽"的差别：同样要"缝"，传输环把缝写进数据流（Link 自描述）；事件环把缝写在流外面的表里（ERST：基址＋大小）。两套方案解决同一个问题——环没有尽头，接缝处不能被当成普通 TRB 误解。这也回答了本章开头的问题：事件环为什么没有 Link TRB——它的回绕不住在环里，登记在寄存器与 ERST 段表中（三级登记链见本章开头）。底部的设备泳道是全课立法的第一现场对照：两种缝法都登记在共享内存与寄存器里，设备一种也看不见。

第 3 章 · 四把钥匙拧一圈：cycle bit × toggle cycle × chain bit × Link TRB

四把钥匙里 cycle 与 Link 在本课第 1、2 章各自独舞过；chain 与 TC 的独舞在上一课（0006 的三层语法与环几何两节）——现在让四把钥匙在同一颗环上咬合转动。先把四者的分工与关系钉成一张表（这张表就是整个动画的说明书，四个"住在哪"一列看完就知道它们谁也不碰谁）：

钥匙住在哪谁写谁读/执行节奏
cycle bit
（DW3 bit0）		每一颗 TRB生产者发布时写消费者取指时校验每颗 TRB 一次
toggle cycle
（Link 的 DW3 bit1）		只在整环最后一段的 Link TRB建环/扩容时定死跨缝的双方各自执行翻转每圈一次（只在接缝）
chain bit
（DW3 bit4）		能串件的数据 TRB（bulk/int/isoc）；TD 跨缝时 Link 也被改写挂上。控制传输没有这把钥匙（见表下注）排 TD 的软件写xHC 沿链续读每个 TD 边界一次
Link TRB
（整颗 16B）		每段末槽（＝接缝）建环写死＋跨缝改写xHC 跳转依据每段一颗

第四把钥匙不是人人都有：chain 只装在"能被串进同一件"的 TRB 类型上——bulk/interrupt/isoc 的数据 TRB（本动画全是 bulk），加上 TD 跨缝时被软件改写挂绳的 Link TRB；控制传输没有这把钥匙——Setup 段 DW3 bit4:1＝RsvdZ，无位可设（Table 6-26）；Data/Status 段虽有 CH 位，内核控制路径全程写 0，分件由三段类型语法自己扛（TRT 预告＋Status 收口）——完整立法与键盘枚举实弹见姊妹课 0009 一场传输的三视角剧。

一句话关系：Link 管几何（在哪接缝）· cycle 管所有权（哪一圈的货）· TC 管换圈（过缝翻轮次）· chain 管打包（几颗 TRB 算一件）。布景：8 槽小环（槽0-6 数据、槽7 固定 Link，TC=1；刻意取小，逼第三颗 TD 撞上接缝），连续排三颗 130KB bulk IN TD（每颗 64K+64K+2K 三个 TRB——切分法与 0006 的 bulk OUT 场景同一套，方向互为镜像：那边软件发货，这边设备回货，货由 xHC 按合同 DMA 直写进软件内存）。两枚游标：▲=软件 enqueue、▼=xHC dequeue。读图色板（每帧同一套）：

第 1 帧空环开局——"空"就是 cycle 不匹配

本帧只看槽0：cyc=0 ≠ 两侧轮次 1——这就是"空"（第 1 章独舞第 1 帧同款）。空环不需要任何标志槽：槽0 cyc=0，与两侧轮次 1 都不匹配，xHC 顺序扫描停在第一个不匹配处（§4.9.2）——不匹配=空。软件侧 cycle_state 初值 1；硬件侧轮次由端点上下文 tr_dequeue 的 DCS 位（Dequeue Cycle State）随游标一起种成 1（Initialize Endpoint 时写入）。生产/消费合同从第一颗 TRB 之前就已经成立。三条泳道同框看一眼：此刻软件在写内存、xHC 在读内存、设备在等令牌——环上的一切它看不见。

130KB 被 64K 边界切成 64K+64K+2K 三颗（0006 三层语法）。本帧只看槽0 与槽1/2 的 cyc 差别：trailing TRB 落地时就带当前轮次现写现发（field |= ring->cycle_state），首 TRB 却故意写成反极性——看上面 ★注记：两条分支殊途同归，写的都是 start_cycle 取反（start_cycle=1 就保持 0、start_cycle=0 反而置 1），整颗 TD 建完才由 giveback_first_trb 一步翻成真值（真值表第三列；翻转代码 :3441-3451——wmb 之后才动首 TRB 的 cycle，随后敲铃）。为什么要反着写？若首 TRB 直接写 0，而本圈轮次恰好是 0（start_cycle=0），半成品首 TRB 会立即匹配、被 xHC 当成品取走；写反值保证整颗 TD 建完之前首 TRB 必不匹配。槽1/2 提前变绿为什么无害？门只开在链头：xHC 严格顺序扫描，过不了槽0（不匹配），永远到不了槽1。chain=1→1→0 加尾 TRB 的 IOC，就是这条 TD 的件界标记与完成触发。

第 4 帧TD1/TD2 相继完成——消费者不擦，生产者覆写

本帧只看消费后的槽色：残影＝不擦除的旧 cyc。TD2 与 TD1 同节奏（完整落在本圈内：压着→发布→敲铃→消费）。看点在槽子：TD1 的三颗 TRB消费后内存里仍写着 cyc=1——消费者不擦除，复用=生产者直接覆写。安全覆写灰槽的前提是 xHC 游标早已越过；而"还有多少槽可写"由 prepare_ring 事前数余量把关（不足→动态扩容，0006 钻点二），cycle 管的是"旧内容不被误读"——两道闸各管一头。回程上两颗 Success 事件也按 cyc=1 进事件环：那里 xHC 是生产者、软件按 unhandled_event_trb(:137) 校验消费——同一份合同站到了对面。两个"时机"读图时容易读丢，钉一遍：① 事件环的写入逐颗对齐——xHC 不攒账，TD1 的尾 TRB（IOC=1）执行完当场写 EV1、翻事件 cycle、拉中断，TD2 完成再写 EV2（放大镜右下角时机注）；② 线上按件推进——xHC 先消费 TD1（逐包 ①IN 令牌→②DATA→③ACK，64K+64K+2K），TD1 收口后才轮到 TD2 的三颗，不存在"收齐两件才开始发 IN 令牌"（线上通道从左到右＝一包事务内的先后）。三视角同框看一眼：设备泳道本帧有戏——两件货各 130KB 已按 IN 令牌逐包回完，货走的路＝设备→线上→xHC→DMA 直写软件内存（Buffer Pointer 合同登记的三段地址），软件从头到尾没碰过一个包；两颗 Success 是完税回执——回执落环时，货早已在软件内存里。

第 6 帧xHC 跨缝——轮次对表，槽0/1 变绿

本帧只看 xHC 轮次盒 1→0 的瞬间：槽0/1 由淡蓝虚线转绿。TD3 已发布（槽6 cyc→1）、门铃已敲。xHC 消费完槽6，行至槽7：Link 的 cyc=1 匹配（上帧生产者翻的极性正是第 N 圈接缝的通行凭证），执行跳转，并按 TC=1 把自己的轮次 1→0——槽0/1 由淡蓝瞬间转绿："有效"是轮次的函数。两个时钟域从不同步全局状态，只在接缝处对一次表。Link TRB 的职责至此凑齐：指针（下一槽/首槽）、TC（对表指令）、自身 cyc（接缝凭证）、chain（"缝在 TD 里"的跨缝胶水）；多段环里它兼任段与段的拼接（0006 钻点二）；事件环则一个都没有——几何外置 ERST（本课第 2 章）。设备泳道再记一笔：TD3 三段 130KB 的回货与 DMA 直写和接缝对表在同一口钟上交错——跳转与对表只发生在共享内存与 xHC 内部，线上只有令牌、数据包与握手。

第 7 帧追平收官——同一颗环，第二轮

本帧只看两枚轮次盒＝0：物理上同一颗环，逻辑上已是第二轮。dequeue 追平 enqueue（同停槽2），环再度为空——但两侧轮次已是 0：物理上同一颗环，逻辑上第二轮。槽0/1 残影的 cyc=0 恰等于当前轮次，看着"有效"——但游标永不回头：环空=xHC 停在第一个不匹配处，假绿的残影永远不会被回头看第二眼。合同不靠擦除、不靠标志位，只靠"轮次+单向扫描"。四把钥匙收拢：cycle=每颗 TRB 的锁（当前轮次=有效）、toggle cycle=翻圈凭证（TC 只挂 last_seg 段尾）、chain=捆绑绳（TRB→TD 的边界）、Link TRB=接缝本身＋对表指令——生产者与消费者各执同一套规则的两半。

一句话收拢：cycle bit 是"每颗 TRB 的所有权"——生产者发布时置成当前轮次，消费者取指时对自己的轮次校验；toggle cycle 让两侧在接缝处（且只在接缝处）同时翻圈，chain bit 把可串件的数据 TRB 捆成 TD 并声明边界（控制传输无此钥匙——件界写在类型语法里，见 0009），Link TRB 身兼指针/TC/自身 cyc/chain 四重身份——四把钥匙咬合，这颗无锁的环才从来不必说出"空"或"满"。生产/消费两侧的动作对照：软件 giveback_first_trb（发布翻 cycle）↔ xHC 取指校验；软件 inc_enq_past_link（跨缝翻轮次）↔ xHC 按 TC 翻轮次；事件环上两套动作整个对调。设备全程不在场：三件 390KB 它只见过令牌与握手，环上的一切对它不可见。

第 4 章 · 圈界与件界：分件的是谁？（读者原问）

这一问不是编的——三课上线当天（2026-10-09），一位读者读完 0006 当场问出；消化后又追出「为什么非要翻圈」（第 5 章）。两问一前一后，恰好把四把钥匙的分工逼到墙角。先钉两个本章的词（首次出现即定义）：

术语管什么哪几把钥匙判的是
圈界这颗槽里的 TRB 属于第几圈cycle bit ＋ toggle cycle本轮新 TRB（有效）vs 旧圈残影——所有权
件界这颗槽是不是一件货（TD）的尽头chain bit ＋ IOCTDn vs TDn+1——打包边界＋收口对账
读者问一（原话复述）：「多段环转一整圈，cycle_state 只翻一次——一个 TD 里的 cycle state 不是都相同吗（除了最后一颗）？那 xHC 怎么区分 TDn 和 TDn+1？」

这句提问把两把钥匙的规则记混了：括号里那条「除最后一颗外都相同」其实是 chain 的规则（TD 内除尾 TRB 外 chain=1、尾 chain=0——0006 的钉死句是「边界＝chain 0」），被记到了 cycle 头上。于是前提看起来全对：同圈内 TD 的 cycle 确实全都相同——但「分件」从来不是 cycle 的工作，就像责怪体重秤量不出身高：它不是干这个的。下面四帧让 cycle 与 chain 第一次同框对照（此前只有独舞与四钥匙齐转，缺的正是并排的这一帧）。布景与色板与第 3 章完全同一套（读图色板见第 3 章开头，此处不重复）——还是那三颗 130KB 的 bulk IN TD；本章新增的镜头语言只有一种：每颗槽角上的「轮次贴纸」＝槽里印的 cyc 值（第 5 章第 3 帧起用）：

第 1 帧同圈的邻居——假悖论定格：六颗 TRB 的 cyc 全部相同

本帧只看槽2 与槽3 这对邻居：TD1 与 TD2 同圈相邻，六颗 TRB 的 cyc 全部＝1，两件之间连一颗空槽都没有隔开——「cycle 全同 ⇒ 分不出 TD」的前提此刻完全成立。它不是环的缺陷：cycle 从没领过「分件」的任务（下一帧看真正管分件的章）。顺带把假悖论的来路钉死：把 chain 的规则（除尾 TRB 外都相同）背到 cycle 头上，两把钥匙在这一帧确实长得像。

第 3 帧反证：跨缝的一件货，身上同时盖着两个圈的章

本帧只看一件货身上的两种圈号：TD3 发布后（槽6 翻成 1），同一件里首 TRB 属缝前的圈、trailing 属缝后的圈（联动第 5 帧排队中途那次轮次翻转的遗产）。若 cycle 真是件界机制，同一件内圈号就不该中途变——它偏偏只在「过缝」时变，与件边界毫无对齐关系；反过来说，「TD 内 cycle 恒相同」连不变量都不是（跨缝即破）。这是比职责表更硬的反证：cycle 不可能承担分件。另一枚方向性证据：cycle 全环唯一的「反常」在首 TRB（发布前反极性压着，联动第 2 帧），不在收口的尾——若它管分件，例外该出现在边界处才对。

第 4 帧一件一票——件界的对账面：票数与票面

本帧只看事件环的票数与票面：每颗 TD 恰一颗收口 Transfer Event（尾 TRB 的 IOC 点亮的回执；bulk 件界口径——控制读一件收两票：Data 短包的中途报账票＋Status 收口票，对照见 0009 传输剧），事件 DW0-1 回指那颗尾 TRB 的地址——软件拿它反查票根 td->end_trb（第 2 帧立法码最后两行记下的就是它），完成收货对账。软件侧从来不需要「数 TRB」来对账：件界三件套＝chain=0（在哪收口）· IOC（收口即出事件）· 尾 TRB 地址（事件回指、对账到件）。底部设备泳道照例是盲区：这三件三票的对账发生在两颗共享内存环上，bulk IN 的设备只见过令牌与握手。

问一收拢：圈界（cycle/TC：本轮新 TRB 还是旧圈残影）与件界（chain：同一件还是下一件）是两个相互独立的检查——xHC 对每颗 TRB 各做一遍，互不影响。把 chain 的规则背到 cycle 头上（「除尾 TRB 外都相同」），就会从「cycle 全同」推出「分不出 TD」的假悖论——分件从来由 chain=0 声明，配 IOC 的一件一事件对账；跨缝一件两章（第 3 帧）是「cycle 不可能管分件」的实锤反证。

第 5 章 · 残影与圈计数：为什么非要翻圈？（读者原问）

读者问二（同日隔一轮的追问）：「TD 已经是最小调度单位了——为什么一圈下来还要按 TC 翻转？这套机制不翻不行吗？」

这一问已经越过「记串钥匙」，直指机制的存在动机。一句话答案：TD 回答「这件传输怎么执行、何时算完成」；cycle/TC 回答它上游的问题——环形缓冲的固定槽位上，「空」与「有新 TRB」怎么分辨。把环想成驿站货架（比喻：环＝快递驿站里一圈固定的格子架，软件＝贴单员，xHC＝取件员；提单贴在格子上、货不在格子上——0006 的货运比喻原样沿用）。三个约束把「怎么分辨新旧」的答案逼成唯一形状：

第 1 帧货架不撕单——消费完的环在内存里的样子

第 2 帧追平之后：同一颗槽，两种真相

本帧只看「答案写在哪」：游标追平后（dequeue 与 enqueue 同指一颗槽），这颗槽里可能是残影（该停）也可能是刚发布的新单（该取）——格子地址相同、游标位置相同，真相却有两种。CPU 与 xHC 之间没有可查询的第三状态库（两时钟域、无锁、唯一通道＝内存），所以「新/旧」必须由格子里的内容自己声明——这就是轮次贴纸的岗位。

第 3 帧轮次贴纸——残影自动失效＝比对不通过，不是撕单

本帧只看角上的贴纸与本周章（第 1 章第 3 帧的贴纸重排版）：「有效」不是格子的属性，是「贴纸对上本周章」这一比对的结果；旧单没人撕，只是再也对不上——失效是被动的、比对出来的（回测考点：残影为什么自动失效）。贴纸只需两种面值（0/1）——为什么两种就够？下一帧。

	}

本帧只看「为什么 1 bit 够用」：软件 enqueue 永远不会领先 xHC dequeue 一整圈——每排一批前 prepare_ring 先数余量（xhci_num_trbs_free），不够先扩容（命令环禁扩、直接拒绝；贴码）。于是任一时刻环上至多两代 TRB（上一圈残影＋本圈新 TRB），奇偶两态判别足矣：把两侧各自维护的「圈计数器」压进内存，只剩末位可写——这就是 cycle_state＝计数器 mod 2；过缝时 TC 让两侧各自 +1（联动第 5/6 帧那次翻转），高位谁也不需要看见。环形缓冲最经典的「游标追平＝空还是有货」难题，xHCI 的答卷：1 bit 数据＋1 bit 进位指令——不用计数器、不用标志位、不用锁。

问二收拢：TD 回答「这件传输怎么执行、何时算完成」；cycle/TC 回答它上游的问题——固定槽位的环形缓冲上「空还是有新 TRB」如何无锁分辨。三个约束（消费不擦除 / 两时钟域无锁 / 唯一通道是内存）把答案逼成唯一形状：新旧写进每颗 TRB（DW3 bit0 的 cyc 值）＋过缝进位（TC）。翻圈不是给 TD 用的，是给环的空满判别用的。

回到整体（环机制收官，传输剧开演）

本课把环自己的事讲完了：cycle 合同（数据先落、cycle 后翻；谁生产谁翻转发布、谁消费谁校验匹配；跨缝由 TC 对表）＋接缝（传输环缝在流里＝Link TRB，事件环缝在表里＝ERST 三级登记链）＋四把钥匙联动（cycle 管所有权、TC 管换圈、chain 管打包、Link 管几何）＋圈界与件界（两个独立检查：cycle 判圈、chain 判件）＋残影与圈计数（1 bit 状态位＋1 bit 进位指令，无锁分辨空满）。三视角立法贯穿全课——环对设备不可见：环住在只有软件与 xHC 能读写的共享内存里，设备只看得见线上：cycle 翻转、Link 跳转、轮次对表、事件回执，设备一样也看不见；它能参与的只有令牌、数据包与握手。

但环只是舞台——一场完整传输的戏还没开演：urb 怎么被打包成五层上环、键盘枚举怎么一部动画演完、Data 段的货谁生产、xHC 怎么用事件通知驱动（事件是完税回执，不是取货单）、TD 的两本账怎么对——这些在姊妹课 0009 一场传输的三视角剧接棒；错误路径与端点命运（CC 判决表、ep_state 十旗标、M4.5 set_address 九事件标本）由 0008 旅程实战与命运收官。hub 线视角的呼应：0002 课你看到的是"主机复位端口、设备拿到地址"；本课之后你知道那背后是 PORT 事件、命令环上的 Address Device 命令、事件环上的回执。
