整体定位（零件已认完，本课让环转起来）

上一课（0006 先认零件）把静态面讲清：TRB 16 字节的每个字段（DW0-1 四种身份、DW2 长度与剩余包数、DW3 控制位）、槽→TD→段→环的组织、切分语法与扩容几何——零件都在桌上，但环还没转。本课收窄为环机制课：只讲环自己怎么转。主角三个：cycle 合同（谁拥有哪颗槽——环形缓冲不用"空/满"标志位的设计答案）、回绕点（内存里的直线怎么闭合成圆）、四个控制位联动（cycle × toggle cycle × chain × Link 在同一颗环上配合）；收官两章接住 2026-10-09 三课上线当天读者的两个真实追问（分件的是哪把控制位？为什么非要翻圈？），把四个控制位的分工逼到墙角再讲一遍。全部动画统一三视角时间轴——软件（驱动）｜xHC 控制器｜设备固件，线上通道画在 xHC 与设备之间；一场完整传输的三视角剧（urb→ring 五层包裹、键盘枚举、Data 段生产者与事件通知链、TD 两套口径）在姊妹课 0009 一场传输的三视角剧开始。术语约定：本课 TD 默认指规范 TD（§4.9.1：一串 TRB 构成的一件传输）；内核 struct xhci_td 的记录粒度不同——两套口径的对照 0009 挑明。

全课通用约定：环对设备不可见——环住在只有软件与 xHC 能读写的共享内存里，设备只看得见线上。传输环、命令环、事件环、ERST 段表全住在主存里，门铃寄存器住在 MMIO 里；设备固件的世界观里只有令牌（token）、数据包与握手。本课每部动画的设备时间轴都按这条约定画：环上独角戏的帧，设备时间轴是「盲区声明」固定框（灰底）；有线上戏份的帧（第 3 章 bulk IN 联动），设备时间轴画同期线上活动与 DMA 直写。

第 1 章 · cycle 位：环的生产/消费合同

环形缓冲没有"空/满"标志位——软件与 xHC 是两个独立时钟域的写者/读者，xHCI 的设计答案是 cycle bit（TRB 控制字段 bit0，§4.11.1 TRB Template）：每个环有当前轮次（0 或 1），生产者填好 TRB 数据后把 cycle 置成当前轮次=发布；消费者只取 cycle 匹配的 TRB；写者追上读者一圈后轮次翻转，旧 TRB 的 cycle 自然失效。三种环的角色分工内核注释讲清：

xhci-ring.c:276 注释原文："See Cycle bit rules. SW is the consumer for the event ring only."——传输环/命令环：软件生产、xHC 消费；事件环：xHC 生产、软件消费。生产/消费两侧各有一套翻转逻辑。

生产者侧的翻转带着一道写屏障——先把 TRB 数据写完，再动 cycle，顺序不可颠倒：

cycle 这个控制位先单独转一圈——三帧只看 cyc 与轮次的比对（其余三把控制位全部静音：每颗 TD 只有 1 颗 TRB、不跨回绕点、不谈 chain 细节；无 JS 时全部帧定格可读）：

第 1 帧"空"＝cyc 不匹配——环上没有任何标志位

本帧只看槽0：cyc=0，两侧轮次都是 1——不匹配。xHC 顺序扫描，停在第一个不匹配处（§4.9.2）：这就是"空"。环形缓冲没有任何"空/满"标志位，"空"是读出来的，不是标出来的。

第 2 帧发布＝把 cyc 写成当前轮次；消费＝校验通过后取走

本帧只看槽0 的 cyc=1 是怎么来的：软件先把数据写进 DW0-2，wmb() 之后才把 DW3 的 cyc 写成 1（＝当前轮次）——这一写就是"发布"。写门铃，xHC 校验 cyc==自己轮次 → 取走。注意"绿"不是槽的属性，是"cyc 与轮次比对通过"这一事件的状态；消费后槽里 cyc=1 原样留着（旧值残留），没人去擦。

第 3 帧第 2 圈：同一个槽，靠另一个 cyc 值再绿一次（N 颗 TD 已略）

本帧只看槽0 的两段历史：上一圈它靠 cyc=1 绿过（那个 1 现在还留在槽里，成了上一轮的旧值残留）；这一圈软件重写 cyc=0，它又绿了。同一个槽、两种"绿"——"有效"从来不是槽的属性，是"cyc 是否等于当前轮次"的比对结果。旧值残留 cyc=1 在轮次 0 下自动作废，谁也不用去擦：这就是无锁环形缓冲从不需要"擦除"的全部秘密。

一句话小结：cycle bit 是无锁环形缓冲的空满合同——先落数据、再翻 cycle（wmb 保证）；谁生产谁翻转发布，谁消费谁校验匹配；跨圈由 Toggle Cycle 位让双方轮次同步翻转。

第 2 章 · Link TRB 与回绕：事件环为什么没有

传输环 / 命令环事件环（§4.9.4）
段尾标记Link TRB（§4.11.5，Fig 4-15）——下一槽指针+Toggle Cycle+Chain无 Link TRB——段的范围由 ERST 段表（§6.5）的"基址+大小"声明
回绕机制xHC 扫到 Link TRB，跳指针、按需翻轮次xHC 写到段尾（地址=基址+（大小−1）×16）即回下一段/首段；软件侧 inc_deq 用 last_trb_on_seg/last_trb_on_ring 判段尾（:191-198）
多段衔接Link TRB 链成环ERST 条目数组顺序衔接（Event Ring Segment Table，Table 6-95）
指针寄存器命令环 CRCR（§5.x，RsvdP 位防软件偷写）ERDP（软件消费到哪，§4.9.4：软件写 ERDP 必须"前进"，xhci-ring.c:3026 注释原引）

为什么事件环不需要 Link TRB？两颗环对"回绕点登记在哪"的答案不同：传输环在数据流里自描述——xHC 扫描时只认 TRB，"下一颗去哪"只能写进流内，Link 亲自占末槽报路；事件环登记在环外，登记链三级：① 寄存器（每颗事件环一组，§5.5.2.3，p425-428）——ERSTSZ 登记共几段、ERSTBA 登记段表本身放在内存哪个地址、ERDP 登记软件消费到哪（xHC 据此回收槽位；软件写它必须"前进"，见上表末行）；② ERST 段表（Event Ring Segment Table，§6.5/Table 6-95，p514-515）——放在系统内存里的条目数组，每条 16 字节＝8 字节段基址（64B 对齐）＋2 字节段大小（段内 TRB 颗数，合法域 16–4096；第 3 帧图里的"大小 8"是画图取小）；③ 段行走（§4.9.4，p179）——xHC 从第 1 段首槽起逐颗写事件，段尾＝基址＋（大小−1）×16——纯算术算出，不读任何 TRB 内容就知道该跳；到段尾翻表的下一条跳下一段基址，最后一条读完绕回第 1 段（初始化序＝写 ERSTSZ→ERDP→ERSTBA，ERSTBA 写下即启动事件环，§4.2）。所以事件环里每一颗槽都是有效载荷，没有一颗要为"报路"牺牲——回绕点住在寄存器与表里，不住在环里。两套方案解决同一个问题：环没有尽头，回绕点总得登记在一个可靠的地方。实现≠规范 内核对特定厂商硬件还有一个规范没有的防御：ETRON 主控上若 Setup/Data 段恰好跨 Link TRB 会被打断，驱动主动垫一个 No-Op TRB 避开回绕点（queue_ctrl_tx 头部 quirk 分支，xhci-ring.c:3775 起）——评审 quirk 补丁时先问"它防的是哪家硬件的什么行为"。

回绕点也单独量一遍——三帧只看"直线怎么变成圆"与"回绕点的两种登记法"（cycle/chain 全部静音）：

第 1 帧内存里的真实形态：环就是一条直线

本帧只看"圆"的真相：内存里没有圆。xHC 走到段末 0x1070 再 +16 就踏出这段了——没有任何自然机制把它送回 0x1000。"环形"是造出来的假象，回绕点就是造这个假象的地方。

第 2 帧走完末槽跳回首槽——这一跳就是回绕点；Link TRB 是回绕点上的路标
指针：下一槽地址（单段环指回首槽，多段环指向下一段首槽） ② 控制字 bit1＝TC（Toggle Cycle）：过回绕点翻轮次的指令 ③ 自己的 cyc 位：这个回绕点本轮的通行凭证　　④ chain 位：TD 跨过回绕点时的续链手段 软件（驱动） Link 的写者：建环时写死指针/TC/自身 cyc；排 TD 跨过回绕点时改写 chain（:277-280） xHC 控制器 Link 的读者：type＝Link 即跳转指针、按 TC 翻轮次、按 chain 续链 USB 线（本阶段静默——回绕点住在内存里，不上线） 设备固件 本阶段设备无戏份——环上的事只发生在软件与 xHC 之间，设备只看得见线上。 回绕点与四个字段全在共享内存里——设备只等线上令牌

本帧只看段末槽：这颗槽住不得数据 TRB。回看第 1 帧底注——xHC 取指就是"读内存、地址每次 +16"：读完一颗，指针落在下一颗，再按那颗 DW3 的 type 字段判断"这是什么、该怎么处理"（type＝每颗 TRB 自带的操作码，正常情况下轮子本来就是靠它分发的）。数据 TRB 的操作码只说"搬这坨数据"，不携带"下一颗去哪"——若末槽放数据 TRB，xHC 读完它，指针 +16 就踏出段外，把环外不相干的内存当作下一颗 TRB 解析、按其中的 type 照常分发执行；那里没人保证是合法 TRB，行为彻底失控。所以末槽固定住 Link TRB：type＝Link 本身就是一条"跳转"操作码——把指针改写成 DW0-1 里的地址，安全送回首槽，Link 就是回绕点的实体。四个字段正好是另外三把控制位的家：指针管"跳去哪"，TC 管过回绕点翻不翻轮次，自身 cyc 管这个回绕点本轮通不通，chain 管 TD 跨过回绕点时链有没有断。

第 3 帧同一个回绕点，两种登记法：传输环回绕点在流里，事件环回绕点在表里

本帧只看两个"末槽"的差别：同样要标记回绕点，传输环把回绕点写进数据流（Link 自描述）；事件环把回绕点写在流外面的表里（ERST：基址＋大小）。两套方案解决同一个问题——环没有尽头，回绕点处不能被当成普通 TRB 误解。这也回答了本章开头的问题：事件环为什么没有 Link TRB——它的回绕不住在环里，登记在寄存器与 ERST 段表中（三级登记链见本章开头）。底部的设备时间轴是全课约定的第一现场对照：两种登记法都落在共享内存与寄存器里，设备一种也看不见。

第 3 章 · 四个控制位拧一圈：cycle bit × toggle cycle × chain bit × Link TRB

四个控制位里 cycle 与 Link 在本课第 1、2 章各自单独演示过；chain 与 TC 的单独演示在上一课（0006 的三层语法与环几何两节）——现在让四个控制位在同一颗环上配合运转。先把四者的分工与关系列成一张表（这张表就是整个动画的说明书，四个"住在哪"一列看完就知道它们谁也不碰谁）：

控制位住在哪谁写谁读/执行节奏
cycle bit
（DW3 bit0）		每一颗 TRB生产者发布时写消费者取指时校验每颗 TRB 一次
toggle cycle
（Link 的 DW3 bit1）		只在整环最后一段的 Link TRB建环/扩容时定死回绕时双方各自执行翻转每圈一次（只在回绕点）
chain bit
（DW3 bit4）		能串件的数据 TRB（bulk/int/isoc）；TD 跨过回绕点时 Link 也被改写挂上。控制传输没有这个控制位（见表下注）排 TD 的软件写xHC 沿链续读每个 TD 边界一次
Link TRB
（整颗 16B）		每段末槽（＝回绕点）建环写死＋回绕时改写xHC 跳转依据每段一颗

第四个控制位不是人人都有：chain 只装在"能被串进同一件"的 TRB 类型上——bulk/interrupt/isoc 的数据 TRB（本动画全是 bulk），加上 TD 跨过回绕点时被软件改写挂绳的 Link TRB；控制传输没有这个控制位——Setup 段 DW3 bit4:1＝RsvdZ，无位可设（Table 6-26）；Data/Status 段虽有 CH 位，内核控制路径全程写 0，分件由三段类型语法自己扛（TRT 预告＋Status 收尾）——完整约定与键盘枚举实弹见姊妹课 0009 一场传输的三视角剧。

一句话关系：Link 管几何（回绕点在哪）· cycle 管所有权（哪一圈的数据）· TC 管换圈（过回绕点翻轮次）· chain 管打包（几颗 TRB 算一件）。布景：8 槽小环（槽0-6 数据、槽7 固定 Link，TC=1；特意取小，让第三颗 TD 恰好撞上回绕点），连续排三颗 130KB bulk IN TD（每颗 64K+64K+2K 三个 TRB——切分法与 0006 的 bulk OUT 场景同一套，方向互为镜像：那边软件发送，这边设备回数据，数据由 xHC 按合同 DMA 直写进软件内存）。两枚指针：▲=软件 enqueue、▼=xHC dequeue。读图色板（每帧同一套）：

第 7 帧追平收官——同一颗环，第二轮

本帧只看两枚轮次盒＝0：物理上同一颗环，逻辑上已是第二轮。dequeue 追平 enqueue（同停槽2），环再度为空——但两侧轮次已是 0：物理上同一颗环，逻辑上第二轮。槽0/1 旧值残留的 cyc=0 恰等于当前轮次，看着"有效"——但指针永不回头：环空=xHC 停在第一个不匹配处，假绿的旧值残留永远不会被回头看第二眼。合同不靠擦除、不靠标志位，只靠"轮次+单向扫描"。四个控制位小结：cycle=每颗 TRB 的锁（当前轮次=有效）、toggle cycle=翻圈凭证（TC 只挂 last_seg 段尾）、chain=捆绑标记（TRB→TD 的边界）、Link TRB=回绕点本身＋核对指令——生产者与消费者各执同一套规则的两半。

一句话小结：cycle bit 是"每颗 TRB 的所有权"——生产者发布时置成当前轮次，消费者取指时对自己的轮次校验；toggle cycle 让两侧在回绕点处（且只在回绕点处）同时翻圈，chain bit 把可串件的数据 TRB 捆成 TD 并声明边界（控制传输无此控制位——TD 边界写在类型语法里，见 0009），Link TRB 身兼指针/TC/自身 cyc/chain 四重身份——四个控制位配合，这颗无锁的环才从来不必说出"空"或"满"。生产/消费两侧的动作对照：软件 giveback_first_trb（发布翻 cycle）↔ xHC 取指校验；软件 inc_enq_past_link（跨过回绕点翻轮次）↔ xHC 按 TC 翻轮次；事件环上两套动作整个对调。设备全程不在场：三件 390KB 它只见过令牌与握手，环上的一切对它不可见。

/* xhci-ring.c:3709-3714（queue_bulk_tx 尾 TRB：清 chain 位＋产生事件＋记末 TRB 记录） */
		if (enqd_len + trb_buff_len >= full_len) {
			field &= ~TRB_CHAIN;
			field |= TRB_IOC;
			more_trbs_coming = false;
			td->end_trb = ring->enqueue;
			td->end_seg = ring->enq_seg;

本帧只看两个位的分家：cycle 位答「新数据还是旧数据」（bit0），chain 位答「同件还是下一件」（bit4）。约定的就是上面两段贴码——排 TD 的软件在 queue_bulk_tx 里逐颗写 chain 位：非尾 TRB field |= TRB_CHAIN＝续链，尾 TRB field &= ~TRB_CHAIN＋TRB_IOC＝收尾、触发事件通知，并记下末 TRB 记录 td->end_trb。同圈邻居 cyc 全同根本不妨碍分件——区分 TDn 与 TDn+1 的从来不是 cycle，是 chain=0 声明 TD 边界、IOC 在 TD 边界处触发事件通知。

第 3 帧反证：跨过回绕点的一件数据，身上同时带着两个轮次的标记

本帧只看一件数据身上的两种圈号：TD3 发布后（槽6 翻成 1），同一件里首 TRB 属回绕点前的圈、trailing 属回绕点后的圈（联动第 5 帧排队中途那次轮次翻转的遗产）。若 cycle 真是 TD 边界机制，同一件内圈号就不该中途变——它偏偏只在「过回绕点」时变，与 TD 边界毫无对齐关系；反过来说，「TD 内 cycle 恒相同」连不变量都不是（跨过回绕点即破）。这是比职责表更硬的反证：cycle 不可能承担分件。另一枚方向性证据：cycle 全环唯一的「反常」在首 TRB（发布前反极性压着，联动第 2 帧），不在收尾的尾——若它管分件，例外该出现在边界处才对。

第 4 帧一个 TD 一颗事件——TD 边界的核对面：事件数与事件字段

本帧只看事件环的事件数与事件字段：每颗 TD 恰一颗收尾 Transfer Event（尾 TRB 的 IOC 点亮的事件通知；bulk TD 边界口径——控制读一件收两事件：Data 短包的中途上报事件＋Status 收尾事件，对照见 0009 传输剧），事件 DW0-1 回指那颗尾 TRB 的地址——软件拿它反查末 TRB 记录 td->end_trb（第 2 帧示例代码最后两行记下的就是它），完成接收核对。软件侧从来不需要「数 TRB」来核对：TD 边界三件套＝chain=0（在哪收尾）· IOC（收尾即出事件）· 尾 TRB 地址（事件回指、核对到件）。底部设备时间轴照例是盲区：这三件三事件的核对发生在两颗共享内存环上，bulk IN 的设备只见过令牌与握手。

问一小结：环的边界（cycle/TC：本轮新 TRB 还是旧值残留）与 TD 边界（chain：同一件还是下一件）是两个相互独立的检查——xHC 对每颗 TRB 各做一遍，互不影响。把 chain 的规则背到 cycle 头上（「除尾 TRB 外都相同」），就会从「cycle 全同」推出「分不出 TD」的假悖论——分件从来由 chain=0 声明，配 IOC 的一个 TD 一颗事件；跨回绕点的一个 TD 带两个轮次（第 3 帧），正说明 cycle 管不了分件。

第 5 章 · 轮次为什么必须翻转

读者问二：「TD 已经是最小调度单位了——为什么一圈下来还要按 TC 翻转？这套机制不翻不行吗？」

这个问题越过规则细节，直指机制的存在动机。简短回答：TD 回答「这件传输怎么执行、何时算完成」；cycle/TC 回答它上游的问题——环形缓冲的固定槽位上，「空」与「有新 TRB」怎么分辨。前提是三个约束：槽位固定、由两个互不查询的时钟域共用、任何一方都不能在对方的寄存器里放状态。三者合起来，把「怎么分辨新旧」逼成唯一形状：

约束① 槽位不回收、旧内容不清除：xHC 对传输环只读不写——取走 TRB 后，槽内字段与 cycle 位原样留着（联动第 4 帧）。只看槽内数据，环永远是「满」的。
↓
约束② 两个时钟域互不查询：CPU 与 xHC 是两个独立时钟域——无锁、无互询；门铃/中断只是「有事情发生」的一锤子通知，不是可查询的状态库。唯一的常设沟通渠道就是共享内存里的环本身——放在任何一方口袋里的「空/满」标志，另一方都看不见。
↓
约束③ ⇒ 新旧只能由每颗 TRB 自描述：DW3 bit0 的 cycle 位——这颗 TRB 是不是本轮的，看这一位对不对得上 xHC 当前轮次。下面四帧只谈 cycle 一个控制位（chain/Link 略去），与第 1 章互为镜像，只是这次问的是「为什么需要它」：
第 1 帧环不回收槽位——消费完的环在内存里的样子

本帧只看「消费完的环」在内存里的样子（联动第 7 帧同款）：七颗旧 TRB 连同轮次位原样躺着，没人擦。若只看槽位内容，「空」与「有数据」无法分辨——这正是问二要拆的难题。下一帧把这个疑问逼到最尖锐的形状。

第 2 帧追平之后：同一颗槽，两种真相

本帧只看「答案写在哪」：指针追平后（dequeue 与 enqueue 同指一颗槽），这颗槽里可能是旧值残留（该停）也可能是刚发布的新 TRB（该取）——槽位地址相同、指针位置相同，真相却有两种。CPU 与 xHC 之间没有可查询的第三状态库（两时钟域、无锁、唯一通道＝内存），所以「新/旧」必须由槽位里的内容自己声明——这就是轮次标记的岗位。

第 3 帧轮次标记——旧值残留自动失效＝比对不通过，不是擦除

本帧只看角上的标记与当前轮次（第 1 章第 3 帧的标记重排版）：「有效」不是槽位的属性，是「标记对上当前轮次」这一比对的结果；旧 TRB 没人擦，只是再也对不上——失效是被动的、比对出来的（回测考点：旧值残留为什么自动失效）。标记只需两种面值（0/1）——为什么两种就够？下一帧。

问二小结：TD 回答「这件传输怎么执行、何时算完成」；cycle/TC 回答它上游的问题——固定槽位的环形缓冲上「空还是有新 TRB」如何无锁分辨。三个约束（消费不擦除 / 两时钟域无锁 / 唯一通道是内存）把答案逼成唯一形状：新旧写进每颗 TRB（DW3 bit0 的 cyc 值）＋过回绕点进位（TC）。翻圈不是给 TD 用的，是给环的空满判别用的。

回到整体（环机制收官，传输剧开始）

本课把环自己的事讲完了：cycle 合同（先落数据、再翻 cycle；谁生产谁翻转发布、谁消费谁校验匹配；回绕由 TC 核对）＋回绕点（传输环回绕点在流里＝Link TRB，事件环回绕点在表里＝ERST 三级登记链）＋四个控制位联动（cycle 管所有权、TC 管换圈、chain 管打包、Link 管几何）＋环的边界与 TD 边界（两个独立检查：cycle 判圈、chain 判件）＋旧值残留与圈计数（1 bit 状态位＋1 bit 进位指令，无锁分辨空满）。三视角约定贯穿全课——环对设备不可见：环住在只有软件与 xHC 能读写的共享内存里，设备只看得见线上：cycle 翻转、Link 跳转、轮次核对、事件通知，设备一样也看不见；它能参与的只有令牌、数据包与握手。

但环只是舞台——一场完整传输的戏还没开始：urb 怎么被分五层打包写进环、键盘枚举怎么一部动画演完、Data 段的数据谁生产、xHC 怎么用事件通知驱动（事件是完成通知，不是索要数据的请求）、TD 的两套口径怎么对——这些在姊妹课 0009 一场传输的三视角剧接棒；错误路径与端点命运（CC 判决表、ep_state 十个状态位、M4.5 set_address 九事件标本）由 0008 旅程实战与命运收官。hub 线视角的呼应：0002 课你看到的是"主机复位端口、设备拿到地址"；本课之后你知道那背后是 PORT 事件、命令环上的 Address Device 命令、事件环上的事件通知。
