    xhci: make sure TRB is fully written before giving it to the controller
    
    Once the command ring doorbell is rung the xHC controller will parse all
    command TRBs on the command ring that have the cycle bit set properly.
    
    If the driver just started writing the next command TRB to the ring when
    hardware finished the previous TRB, then HW might fetch an incomplete TRB
    as long as its cycle bit set correctly.
    
    A command TRB is 16 bytes (128 bits) long.
    Driver writes the command TRB in four 32 bit chunks, with the chunk
    containing the cycle bit last. This does however not guarantee that
    chunks actually get written in that order.
    
    This was detected in stress testing when canceling URBs with several
    connected USB devices.
    Two consecutive "Set TR Dequeue pointer" commands got queued right
    after each other, and the second one was only partially written when
    the controller parsed it, causing the dequeue pointer to be set
    to bogus values. This was seen as error messages:
    
    "Mismatch between completed Set TR Deq Ptr command & xHCI internal state"
    
    Solution is to add a write memory barrier before writing the cycle bit.

背景（何时 / 何硬件 / 谁报）

2021 年 1 月，xHCI 子系统维护者 Mathias Nyman（Intel）合入这枚补丁。问题发现于压力测试：多个 USB 设备同时在线、反复取消 URB 的场景——两条「Set TR Dequeue Pointer」命令背靠背进入命令环，第二条命令 TRB 还没写完就被控制器取走解析。硬件本身没有缺陷，这是纯软件侧的内存序问题：门铃敲响后 xHC 会立即回来解析命令环上 cycle 位已就绪的命令 TRB（§4.1 p68 的发出节拍），而驱动「先写完 TRB、再敲门铃」这个顺序在写缓冲与多核环境下并没有任何机制保证。对应课程 4.1 的三拍：上环→敲门铃→xHC 取指执行，补丁保证第一拍真正先于第二拍对硬件生效。

要解决的问题（症状 + 机制）

症状：压力测试中反复出现 "Mismatch between completed Set TR Deq Ptr command & xHCI internal state" 告警，出环指针被设成 bogus 值。机制：命令 TRB 长 16 字节，驱动分四个 32 位分片写入，含 cycle bit 的分片安排在最后写——但这只是程序顺序，普通 store 不保证实际落盘次序；当前一条命令完成、硬件立刻回来取下一条时，可能读到只写了一半、而 cycle bit 恰好已置位的 TRB，于是照常执行。规范背景（§4.1 p68）：命令的发出流程是「把命令 TRB 放上命令环，然后敲命令门铃寄存器 0」——“放完才敲”的语义在 SMP 下必须由写屏障兑现，否则门铃会抢在 TRB 完整之前通知 xHC。

代码逻辑（补丁前 → 后行为对照）

补丁前：queue_trb() 依次写 field[0..3]，field[3]（含 cycle bit）程序上最后写但无屏障——硬件可能在 field[0..2] 尚未全局可见时就看到 cycle 位翻转，取走半颗 TRB。补丁后：在写 field[3] 之前插入 wmb() 写屏障并加注释行（+2 行），保证前三个分片先于 cycle 位翻转全局可见——“TRB 完整写好才交给控制器”由架构屏障兑现；此后命令完成事件（Command Completion Event，§4.1 p68）回执对应的总是一颗完整 TRB。与代码摘录（drafts/code-excerpts.json cmd 组 L4397 queue_trb(...) 入环行、L438 门铃行）对读，补丁改动恰好落在“写 TRB”与“敲门铃”两拍之间的写路径上；对映课程动画，节拍从此是“写四片 → wmb → cycle 翻转 → 门铃”，任何一环都不会被硬件抢先看到。

背景（何时 / 何硬件 / 谁报）

2026 年 10 月，QNAP（NAS 存储厂商）的 Henry Tseng 报告并提交：xhci_reset() 在主机控制器未 halted（未停机）时直接中止复位路径，却不写 CMD_RESET、也不返回错误。触发场景是主机未停机就有路径对控制器调用复位（驱动探测/恢复流程）。硬件无关——这是纯软件状态机的返回值语义缺陷。对应课程 4.2 的 halt→reset 握手节拍：复位的前提（主机已停机）与完成（CNR 清零）都要靠状态位逐级确认，前提不满足时必须把失败如实上抛，而不是伪装成功。

要解决的问题（症状 + 机制）

症状：调用方检查 xhci_reset() 返回值时被告知「复位成功」，而复位实际上根本没有执行——这是全部复位失败路径里唯一一个「失败却返回 0」的分支。机制：xhci_reset() 开头读 USBSTS 状态，若 (state & STS_HALT) == 0（主机未 halted），按语义复位应当中止；补丁前这个分支 return 0，与后续「写 CMD_RESET → handshake 等 CNR 清零 → 失败返回超时错误」的其他路径语义不一致。规范背景（§4.2 p69）：复位不是瞬时动作，而是带握手的流程——芯片硬件复位后要等 USBSTS.CNR 清零才允许写其它 Operational/Runtime 寄存器；前提不满足就应报错，让调用链不至于在「复位已完成」的假象上继续初始化。

代码逻辑（补丁前 → 后行为对照）

单行改动（drivers/usb/host/xhci.c，xhci_reset）：未 halted 中止分支 return 0 → return -EBUSY。补丁前：中止复位被当成成功，调用方在错误状态下继续走初始化。补丁后：-EBUSY 把「主机忙、未停机」如实上抛，调用方走错误处理——xhci_reset 的所有失败出口（未 halted / handshake 超时）语义一致。与代码摘录（drafts/code-excerpts.json init 组 L229，同函数内 xhci_handshake(&xhci->op_regs->status, STS_CNR, 0, timeout_us)）对读：那条握手失败会返回超时错误，本补丁让“没进入复位”同样返回错误；凡依赖返回值判断复位成败的调用方（探测、休眠恢复、错误恢复路径）从此拿到一致语义，验收时可直接对 -EBUSY 分支验证未停机场景。

    usb: xhci: Set avg_trb_len = 8 for EP0 during Address Device Command
    
    There is a subtle contradiction between sections of the xHCI 1.2 spec
    regarding the initialization of Input Endpoint Context fields. Section
    4.8.2 ("Endpoint Context Initialization") states that all fields should
    be initialized to 0. However, Section 6.2.3 ("Endpoint Context", p.453)
    specifies that the Average TRB Length (avg_trb_len) field shall be
    greater than 0, and explicitly notes (p.454): "Software shall set
    Average TRB Length to '8' for control endpoints."
    
    Strictly setting all fields to 0 during initialization conflicts with
    the specific recommendation for control endpoints. In practice, setting
    avg_trb_len = 0 is not meaningful for the hardware/firmware, as the
    value is used for bandwidth calculation.
    
    Motivation: Our company is developing a custom Virtual xHC hardware
    platform that strictly follows the xHCI spec and its recommendations.
    During validation, we observed that enumeration fails and a parameter
    error (TRB Completion Code = 5) is reported if avg_trb_len for EP0 is
    not set to 8 as recommended by Section 6.2.3. This demonstrates the
    importance of assigning a meaningful, non-zero value to avg_trb_len,
    even in virtualized or emulated environments.
    
    This patch explicitly sets avg_trb_len to 8 for EP0 in
    xhci_setup_addressable_virt_dev(), as recommended in Section 6.2.3, to
    prevent potential issues with xHCI host controllers that enforce the
    spec strictly.

要解决的问题（症状 + 机制）

    xHC controller may immediately reuse a slot_id after it's disabled,
    giving it to a new enumerating device before the xhci driver freed
    all resources related to the disabled device.

    while device-B is enumerating, device-B will fail to enumerate in the
    follow sequence.

    2.[device-B] send enable slot command
    3.[device-A] disable slot command completed and wakeup waiting thread
    4.[device-B] enable slot command completed with slot_id equal to 1 and

    usb: xhci: Correct last context entry calculation for Configure Endpoint
    
    The current XHCI driver recalculates the Context Entries field in the
    Slot Context on every add_endpoint() and drop_endpoint() call. In the
    case of drop_endpoint(), it seems to assume that the add_flags will
    always contain every endpoint for the new configuration, which is not
    necessarily correct if you don't make assumptions about how the USB core
    uses the add_endpoint/drop_endpoint interface (add_flags only contains
    endpoints that are new additions in the new configuration).

    the lifetime of a device. This means that when all endpoints are
    dropped, the Context Entries field can be set to 0 (which is invalid and
    may cause a Parameter Error) or -1 (which is interpreted as 31 and
    causes the driver to keep using the old, incorrect value).

    existing endpoints into account, and to force the value to 1 (meaning
    only EP0 is active) if no other endpoint is found. This patch implements
    that as a single step in the final check_bandwidth() call and removes
    the intermediary calculations from add_endpoint() and drop_endpoint().

背景（何时 / 谁修 / 为什么是它）

2014 年 6 月，Chromium OS 的 Julius Werner 提交、Mathias Nyman 与 Greg Kroah-Hartman 签收。Context Entries 是 Slot Context 里「本槽最后一个有效端点上下文的索引」——§4.6.6 执行算法（p110）规定每次 Configure Endpoint 后由 xHC 收束：全 Disabled 落 '1'，否则落最后有效索引；p111 还规定Add 旗标指到的 DCI 超过该值即 Parameter Error。这个字段的内核侧计算，从环扩张时代起就散落在xhci_add_endpoint()/xhci_drop_endpoint() 里增量维护。

要解决的问题（症状 + 机制）

症状：某些「全部端点被 drop」的配置切换（如切到 Alternate Interface 0）后，Configure Endpoint 命令被 xHC 以 Parameter Error 拒绝，或驱动继续沿用旧值。机制（message 原文）：drop_endpoint() 的增量计算「似乎假定 add_flags 总含新配置的全部端点」——实际 add_flags 只含新配置里新增的端点；且 EP0_FLAG 在设备生命周期里并非恒置。两个假设任一不成立，全 drop 时 Context Entries 就被算成 0（非法值——p111 Parameter Error 判据「Add 的 DCI > Context Entries」直接命中）或 -1（按 LAST_CTX 宏解读为 31，导致继续使用旧的错误值）。

代码逻辑（补丁前 → 后行为对照）
