§4.2主机控制器初始化

①规范与代码分析

规范要点（xHCI 规范 §4.2 · p69-70）

要点 1 · 复位后等 USBSTS.CNR 清零，才能写任何 Operational/Runtime 寄存器

After Chip Hardware Reset6 wait until the Controller Not Ready (CNR) flag in the USBSTS is ‘0’ before writing any xHC Operational or Runtime registers.
- 芯片硬件复位（Chip Hardware Reset）6之后，在写入任何 xHC 操作（Operational）或运行时（Runtime）寄存器之前，先等待 USBSTS 中的 Controller Not Ready（CNR）标志变为‘0’。
—— evidence/spec-42.txt L18-L19（p69）

要点 2 · 各步顺序不强制，但必须在 USBCMD R/S=1 之前全部完成

Note: This text does not imply a specific order for the following operations, however these operations shall be completed before setting the USBCMD register Run/Stop (R/S) bit
注：以上文字并不意味着下列操作必须按特定顺序执行，但在把 USBCMD 寄存器的 Run/Stop（R/S）位置为‘1’之前，这些操作必须全部完成。
—— evidence/spec-42.txt L21-L22（p69）

要点 3 · CONFIG.MaxSlotsEn 使能软件要用的设备槽

Program the Max Device Slots Enabled (MaxSlotsEn) field in the CONFIG register (5.4.7) to enable the device slots that system software is going to
- 在 CONFIG 寄存器（5.4.7）中编程 Max Device Slots Enabled（MaxSlotsEn）字段，以启用系统软件将要使用的设备槽。 - 对设备上下文基地址数组指针（Device Context Base Address Array Pointer, DCBAAP）寄存器（见 5.4.6 节“设备上下文基地址数组指针寄存器（DCBAAP）”）编程，写入 64 位地址，指向设备上下文基地址数组（Device Context Base Address Array）所在的位置。
—— evidence/spec-42.txt L25（p69）

要点 4 · CRCR=命令环首 TRB 地址（含 Cycle 位）

Define the Command Ring Dequeue Pointer by programming the Command Ring Control Register (Section 5.4.5 Command Ring Control Register (CRCR)) with a 64-bit address pointing to the starting address of the first TRB of the Command Ring.
- 通过对命令环控制寄存器（Command Ring Control Register，见 5.4.5 节“命令环控制寄存器（CRCR）”）编程来定义命令环出队指针（Command Ring Dequeue Pointer）：写入 64 位地址，指向命令环第一个 TRB 的起始地址。 - 按如下方式初始化中断7：
—— evidence/spec-42.txt L34-L36（p69）

要点 5 · R/S=1 开机——xHC 从此开始接受门铃引用

Write the USBCMD (5.4.1) to turn the host controller ON via setting the Run/Stop (R/S) bit to ‘1’. This operation allows the xHC to begin accepting doorbell references.
- 向 Interrupter Management 寄存器（5.5.2.1）的 Interrupt Enable（IE）字段写‘1’，启用该中断器。 - 写 USBCMD（5.4.1），通过把 Run/Stop（R/S）位置为‘1’将主机控制器打开（ON）。此操作使 xHC 开始接受门铃引用（doorbell reference）。
—— evidence/spec-42.txt L115-L116（p70）

背景（何时 / 何硬件 / 谁报）

2026 年 10 月，QNAP（NAS 存储厂商）的 Henry Tseng 报告并提交：xhci_reset() 在主机控制器未 halted（未停机）时直接中止复位路径，却不写 CMD_RESET、也不返回错误。触发场景是主机未停机就有路径对控制器调用复位（驱动探测/恢复流程）。硬件无关——这是纯软件状态机的返回值语义缺陷。对应课程 4.2 的 halt→reset 握手节拍：复位的前提（主机已停机）与完成（CNR 清零）都要靠状态位逐级确认，前提不满足时必须把失败如实上抛，而不是伪装成功。

要解决的问题（症状 + 机制）

症状：调用方检查 xhci_reset() 返回值时被告知「复位成功」，而复位实际上根本没有执行——这是全部复位失败路径里唯一一个「失败却返回 0」的分支。机制：xhci_reset() 开头读 USBSTS 状态，若 (state & STS_HALT) == 0（主机未 halted），按语义复位应当中止；补丁前这个分支 return 0，与后续「写 CMD_RESET → handshake 等 CNR 清零 → 失败返回超时错误」的其他路径语义不一致。规范背景（§4.2 p69）：复位不是瞬时动作，而是带握手的流程——芯片硬件复位后要等 USBSTS.CNR 清零才允许写其它 Operational/Runtime 寄存器；前提不满足就应报错，让调用链不至于在「复位已完成」的假象上继续初始化。

代码逻辑（补丁前 → 后行为对照）

单行改动（drivers/usb/host/xhci.c，xhci_reset）：未 halted 中止分支 return 0 → return -EBUSY。补丁前：中止复位被当成成功，调用方在错误状态下继续走初始化。补丁后：-EBUSY 把「主机忙、未停机」如实上抛，调用方走错误处理——xhci_reset 的所有失败出口（未 halted / handshake 超时）语义一致。与代码摘录（drafts/code-excerpts.json init 组 L229，同函数内 xhci_handshake(&xhci->op_regs->status, STS_CNR, 0, timeout_us)）对读：那条握手失败会返回超时错误，本补丁让“没进入复位”同样返回错误；凡依赖返回值判断复位成败的调用方（探测、休眠恢复、错误恢复路径）从此拿到一致语义，验收时可直接对 -EBUSY 分支验证未停机场景。
