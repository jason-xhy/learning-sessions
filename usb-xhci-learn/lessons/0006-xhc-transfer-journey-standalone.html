整体定位（先挂图：hub 线看到的"主机"，本线开箱）

hub 线五课里（0002–0005），"主机"始终是一个黑盒：复位时序、描述符请求、TT split——我们一直站在设备与 hub 侧看主机的行为。本课把黑盒打开：usbcore 之下、xHC 之内，一次控制传输是怎么走完全程的。你在 0001 诊断里 xHCI 骨架域 3/3 全对（三种环 / Doorbell / Table 6-90）——骨架已成体系，xHC 线钻的正是骨架之上的动态细节。

六站旅程（每站一个内核锚点）

① 驱动入队——usbcore 把 urb 交给 xhci-hcd：usbcore 调 hcd 的 urb_enqueue 方法，按端点类型分派；控制传输走 xhci_queue_ctrl_tx（xhci.c:1697）。 
/* xhci.c:1695-1700 */
	switch (usb_endpoint_type(&urb->ep->desc)) {
	case USB_ENDPOINT_XFER_CONTROL:
		ret = xhci_queue_ctrl_tx(xhci, GFP_ATOMIC, urb,
					 slot_id, ep_index);
		break;
↓
② TRB 化——一次控制传输 = Setup/Data/Status 三段 TRB：urb 被改写成 TRB 链排进 endpoint ring（§4.9.1：TD=Transfer Descriptor）。Setup 段 8 字节 setup 包内联进 TRB（IDT，Immediate Data，Table 6-23）；Data 段带 DMA 缓冲指针（IN 方向加 ISP=短包即中断）；Status 段置 IOC=完成即产事件（§4.10.4）。关键动作：先存 start_cycle，三段全部排完才回头翻首 TRB 的 cycle——半成品 TD 对硬件不可见。 
/* xhci-ring.c:3832-3838 */
	/*
	 * Don't give the first TRB to the hardware (by toggling the cycle bit)
	 * until we've finished creating all the other TRBs.  The ring's cycle
	 * state may change as we enqueue the other TRBs, so save it too.
	 */
	start_trb = &ep_ring->enqueue->generic;
	start_cycle = ep_ring->cycle_state;
↓
③ 原子发布 + 敲门铃：Status TRB 排完（IOC 位，xhci-ring.c:3915），调 giveback_first_trb（:3437）——wmb() 写屏障保证"TRB 数据先落、cycle 位后翻"，然后 MMIO 写 doorbell 寄存器（§4.7 Doorbells；寄存器位面 §5.6）：writel 后紧跟 readl 刷写。门铃值=目标端点号（DB_TARGET）。 
/* xhci-ring.c:3446-3459（基线 :3437） */
	/*
	 * Pass all the TRBs to the hardware at once and make sure this write
	 * isn't reordered.
	 */
	wmb();
	if (start_cycle)
		start_trb->field[3] |= cpu_to_le32(start_cycle);
	else
		start_trb->field[3] &= cpu_to_le32(~TRB_CYCLE);
	xhci_ring_ep_doorbell(xhci, slot_id, ep_index, stream_id);
/* xhci-ring.c:569-571（xhci_ring_ep_doorbell :551） */
	writel(DB_VALUE(ep_index, stream_id), db_addr);
	/* flush the write */
	readl(db_addr);
小字：五种端点态不敲铃（EP_STOP_CMD_PENDING|SET_DEQ_PENDING|EP_HALTED|EP_CLEARING_TT|EP_DROP_PENDING，:551 函数头）——halt 中的端点敲了也白敲，还可能打断停止流程。
↓
④ xHC 取指执行——cycle 匹配才取，取完上线：xHC 沿环扫描，只消费 cycle 位等于当前轮次的 TRB（§4.9.2），把三段 TD 翻译成线上事务：Setup 包→数据包→状态握手。控制传输的地址阶段特殊：Address Device 命令 BSR=0 时，SET_ADDRESS 由 xHC 自己上线（驱动从不单独排 SET_ADDRESS 的 TD，§4.6.5）——你在 hub 线 0002 看到的"设备拿到地址 1"，xHC 侧就是这一步。
↓
⑤ 事件回程——event ring + 完成码 CC：xHC 把结果写进 event ring（xHC 生产、软件消费的环，§4.9.4），拉 MSI/线中断。驱动中断入口 xhci_handle_events（:3092）循环消费：unhandled_event_trb（:137）做 cycle 校验，xhci_handle_event_trb（:2992）按类型分派——命令完成→handle_cmd_completion（:1803），传输完成→handle_tx_event（:2632）。完成码 CC 在事件 DW2[31:24]（Table 6-37/6-40），全表=Table 6-91（Success=1、Short Packet=13…）。handle_cmd_completion 还做回执配对：事件里的命令 TRB 指针必须等于命令环 dequeue，否则丢弃（防错配）。 
/* xhci-ring.c:137-141（消费侧 cycle 校验） */
static bool unhandled_event_trb(struct xhci_ring *ring)
{
	return ((le32_to_cpu(ring->dequeue->event_cmd.flags) & TRB_CYCLE) ==
		ring->cycle_state);
}
↓
⑥ 回调——urb 回到 usbcore：TD 全部完成（last_td_in_urb）后 xhci_giveback_urb_in_irq（:807）调 usb_hcd_giveback_urb（:824）→ urb->complete 回调 → usbcore 发下一轮请求。至此闭环，六站走完。

钻点一 · cycle bit：环的生产/消费合同

环形缓冲没有"空/满"标志位——软件与 xHC 是两个独立时钟域的写者/读者，xHCI 的立法答案是 cycle bit（TRB 控制字段 bit0，§4.11.1 TRB Template）：每个环有当前轮次（0 或 1），生产者填好 TRB 数据后把 cycle 置成当前轮次=发布；消费者只取 cycle 匹配的 TRB；写者追上读者一圈后轮次翻转，旧 TRB 的 cycle 自然失效。三种环的角色分工内核注释一句话说尽：

xhci-ring.c:276 注释原文："See Cycle bit rules. SW is the consumer for the event ring only."——传输环/命令环：软件生产、xHC 消费；事件环：xHC 生产、软件消费。生产/消费两侧各有一套翻转逻辑。

生产者侧的翻转带着一道写屏障——先把 TRB 数据写完，再动 cycle，顺序不可颠倒：

生产者：跨段时翻 Link TRB + 轮次取反（传输环，软件是生产者）： 
/* xhci-ring.c:255-262（inc_enq_past_link :234） */
		/* Give this link TRB to the hardware */
		wmb();
		ring->enqueue->link.control ^= cpu_to_le32(TRB_CYCLE);

		/* Toggle the cycle bit after the last ring segment. */
		if (link_trb_toggles_cycle(ring->enqueue))
			ring->cycle_state ^= 1;
实现≠规范 这里藏着一段规范史：xHCI 0.95 说 Link TRB 不得带 chain 位、0.96 errata 才修正——内核对 0.95 老硬件保留 chain 位不改写的兼容分支（xhci_link_chain_quirk，:234 函数头注释）。评审老控制器代码时会再遇到它。
↓
消费者：cycle 匹配才处理，跨段尾时轮次取反（事件环，软件是消费者）——unhandled_event_trb（:137）判"还有没有要处理的事件"，inc_deq（:188）推进游标并在整个环的最后一个 TRB 处翻转软件侧轮次： 
/* xhci-ring.c:191-198（inc_deq :188，事件环特例） */
	/* event ring doesn't have link trbs, check for last trb */
	if (ring->type == TYPE_EVENT) {
		if (!last_trb_on_seg(ring->deq_seg, ring->dequeue)) {
			ring->dequeue++;
			return;
		}
		if (last_trb_on_ring(ring, ring->deq_seg, ring->dequeue))
			ring->cycle_state ^= 1;
一句话收拢：cycle bit 是无锁环形缓冲的空满合同——数据先落、cycle 后翻（wmb 保证）；谁生产谁翻转发布，谁消费谁校验匹配；跨圈由 Toggle Cycle 位让双方轮次同步翻转。

钻点二 · Link TRB 与回绕：事件环为什么没有

传输环 / 命令环事件环（§4.9.4）
段尾标记Link TRB（§4.11.5，Fig 4-15）——下一槽指针+Toggle Cycle+Chain无 Link TRB——段的范围由 ERST 段表（§6.5）的"基址+大小"声明
回绕机制xHC 扫到 Link TRB，跳指针、按需翻轮次xHC 写到段尾（地址=基址+（大小−1）×16）即回下一段/首段；软件侧 inc_deq 用 last_trb_on_seg/last_trb_on_ring 判段尾（:191-198）
多段衔接Link TRB 链成环ERST 条目数组顺序衔接（Event Ring Segment Table，Table 6-95）
游标寄存器命令环 CRCR（§5.x，RsvdP 位防软件偷写）ERDP（软件消费到哪，§4.9.4：软件写 ERDP 必须"前进"，xhci-ring.c:3026 注释原引）

为什么事件环不需要 Link TRB？传输环的接缝必须在数据流里自描述（xHC 扫描时只认 TRB）；事件环的几何在 ERST 表里外置声明（段表本身就是"环的说明书"）——两套方案解决同一个问题：环没有尽头，接缝处不能被当成普通 TRB 误解。实现≠规范 内核对特定厂商硬件还有一个规范没有的防御：ETRON 主控上若 Setup/Data 段恰好跨 Link TRB 会被打断，驱动主动垫一个 No-Op TRB 避开接缝（queue_ctrl_tx 头部 quirk 分支，xhci-ring.c:3775 起）——评审 quirk 补丁时先问"它防的是哪家硬件的什么行为"。

标本解剖 · M4.5 set_address 全握手（自研引擎实测）

以下数字全部来自我们亲手实现的 xHC 引擎 v0.3 仿真（M4.5，合同（作者工作区在案）与日志在案）：事件环只有 6 槽——刻意取小逼出回绕，正好把 0001 骨架里的"三种环"动起来给你看。九条事件全序 = 端口插入 → EnableSlot → Addr BSR=1 → 8B 描述符 → Addr BSR=0 → 64B 描述符（短包）→ ConfigureEP → SET_CONFIG：

驱动发 Enable Slot → Address Device BSR=1（Block Set Address，命令 TRB 的 BSR 位，内核 xhci_queue_address_device xhci-ring.c:4412：SETUP_CONTEXT_ONLY 时打上 TRB_BSR）。BSR=1=只建上下文不设址，设备停在地址 0——于是 TD1 的 GET_DESCRIPTOR(8B)（setup8 逐字节 80 06 00 01 00 00 08 00）在地址 0 上服务（实测 dev_addr=0 通过设备过滤）。这正是 hub 线 0002 课"先取 8 字节定 ep0 包长"的 xHC 侧实现。

驱动发 Address Device BSR=0（SETUP_CONTEXT_ADDRESS，内核 xhci_setup_device xhci.c:4318）。SET_ADDRESS 不是驱动的控制传输——xHC 在总线上自己发（§4.6.5；引擎钩子日志：SET_ADDRESS wire txn addr=1，4.0µs 完成），线上事务完成后才写 CCC 事件（实测日志序：wire txn 行在前、EV5 行在后；A5 断言 PASS）。此后设备在地址 1 服务。规范 §4.3.4 Address Assignment 的两段式（BSR=1 探路、BSR=0 落址）你在 0002 死记过的时序，在这里是两条命令加一颗线上事务。
第 4 帧64B 描述符短包：双事件 + 环回绕 + cycle 轮转
槽0EV7 TR ✓TD2 cyc=0
槽1-4EV1-EV5 ✓
槽5EV6 TR Short 残46 cyc=1
TD2=GET_DESCRIPTOR(64B)（80 06 00 01 00 00 40 00）@地址 1。设备只有 18B → 短包：一条 Short Packet 事件（CC=13，残量 64−18=46）落 Data TRB、一条 Success 落 Status TRB——hub 线 0002 讲的"描述符长度以实际短包为准"，在事件环上是两颗事件。EV6 落槽 5 后环满回绕：EV7 落回槽 0，轮次翻转为 0（实测：前 6 条 cyc=1、后 3 条 cyc=0）——软件消费者的 cycle_state ^= 1（inc_deq）在这次消费里真实执行了一次。

槽1EV8 CC CfgEP cyc=0
槽2EV9 TR ✓TD3 cyc=0
槽3-5（旧轮已消费）

TD3=SET_CONFIGURATION(1)（00 09 01 00 00 00 00 00）两段式单 Success 事件。门铃-消费-事件的闭环六站在九颗事件里全部走过一遍：③每敲一次铃（3 次）→ ④xHC 消费一个 TD → ⑤事件回程（1/2/1）→ ⑥ usbcore 继续。收尾注记：标本≠产品 6 槽事件环是仿真刻意取小逼回绕（真实 xHC 事件环每段 256/512 TRB）；引擎也不建模 slot state=Configured(3)（§4.3.5 有此态，"已配置"以设备侧 configured 标志观测——引擎边界，M4.5 合同 §2.3）。
