标本解剖 · M4.5 set_address 全握手（自研引擎实测）

钻点一 · 四种传输各自的命运：错误路径全图

六站旅程与 M4.5 标本走的都是 happy path（九颗事件全是 Success/Short Packet）。真实总线上会出错——xHCI 把错误立法成两层：完成码 CC（Table 6-91 p507：事件回程携带的"判决书"）与端点状态后果（这个判决会不会让 xHC 侧端点停机）。第二层的裁决函数只有一个，值得整段读：

/* xhci-ring.c:2204-2231（xhci_halted_host_endpoint）——哪些 CC 让 xHC 端点 halt */
static bool xhci_halted_host_endpoint(struct xhci_hcd *xhci, struct xhci_ep_ctx *ep_ctx,
				      unsigned int comp_code)
{
	int ep_type = CTX_TO_EP_TYPE(le32_to_cpu(ep_ctx->ep_info2));

	switch (comp_code) {
	case COMP_STALL_ERROR:
		/* on xHCI this always halts, including protocol stall */
		return true;
	case COMP_BABBLE_DETECTED_ERROR:
		/*
		 * The 0.95 spec says a babbling control endpoint is not halted.
		 * The 0.96 spec says it is. Some HW claims to be 0.95
		 * compliant, but it halts the control endpoint anyway.
		 * Check endpoint context if endpoint is halted.
		 */
		if (xhci->hci_version <= 0x95 && ep_type == CTRL_EP)
			return GET_EP_CTX_STATE(ep_ctx) == EP_STATE_HALTED;

		fallthrough;
	case COMP_USB_TRANSACTION_ERROR:
	case COMP_SPLIT_TRANSACTION_ERROR:
		/* these errors halt all non-isochronous endpoints */
		return ep_type != ISOC_IN_EP && ep_type != ISOC_OUT_EP;
	}

	return false;
}

三个立法要点：① STALL 总是 halt 主机侧端点——包括 ep0 的协议 stall（设备侧 ep0 stall 只是"本请求不支持"，但 xHC 内部状态照样要 Reset Endpoint 清理；设备侧 halt 由类驱动随后发 CLEAR_FEATURE(ENDPOINT_HALT) 清，:2201-2202 注释）；② Babble 在 0.95/0.96 规范间变过卦，内核对声称 0.95 的老硬件改查 EP 上下文实态（:2213-2221，实现≠规范 家族的又一枚）；③ USB Transaction Error / Split Transaction Error halt 一切非等时端点——等时端点天生豁免（§4.10.2.8：等时错误逐帧上报、传输继续，"错一帧不赖整条流"）。另外 USB Transaction Error 在走到这个裁决函数之前，xHC 硬件已经按 EP 上下文的错误计数自行重试过若干轮（§4.10.2.3 / §4.10.2.7 Bus Error Counter）——内核看到的是硬件重试穷尽后的终审判决。

一句话收拢：错误处理的第一道分岔是"会不会 halt"（xhci_halted_host_endpoint），第二道分岔是"按类型分派"（process_ctrl/isoc/bulk_intr_td）——控制传输按阶段记账、bulk 软重试原地再战、等时永不 halt 逐帧判决。halt 之后的恢复链（Reset Endpoint → Set TR Dequeue → 给回 → CLEAR_FEATURE）是端点级的，与传输类型无关——那是钻点二的主角。

钻点二 · ep_state 旗标：软件侧的第二台状态机

0009 开篇六站图 ③站的小字预告过：五种端点态不敲铃。现在把整台机器拆开——xHC 硬件自己有一台端点状态机（Endpoint Context 的 ep_state 字段，§4.8.3 p162，五态），内核在 struct xhci_virt_ep 里又维护一台软件状态机（ep_state 位域，十个旗标）——两台机器通过命令环/事件环对话，谁也不同步谁，全靠这些旗标记住"我这边正在进行什么"：

TT 那一行值得单独展开——它是 hub 线与 xHC 线的交汇点。LS/FS 设备经 TT 的批量/控制传输出错时（0005 课讲的 TT buffer 残留），finish_td 在进入 halt 恢复前先异步发 CLEAR_TT_BUFFER（usb core 的控制传输），期间置 EP_CLEARING_TT；ep0 的 stall 例外不清 TT（:2278——ep0 不经 TT 缓冲）。清完的回调只做两件事：清旗标、敲门铃——排队等待的 URB 这才被 xHC 看见：

	    (td->urb->dev->tt->hub != xhci_to_hcd(xhci)->self.root_hub) &&

			ep->ep_state &= ~EP_CLEARING_TT;

第 1 帧STALL 判决书到达：Transfer Event(CC=6)
软件 ep_state全 0（此前无故障）

命令环—

urb未给回
handle_tx_event 给 td->status 打上 -EPIPE（:2705-2708），分派 process_bulk_intr_td——错误不是终点，urb 还不能给回：得先把 xHC 侧端点从 HALTED 状态捞出来，TD 才能销账。
第 2 帧finish_td 裁决：halt 成立 → 置旗标 + Reset Endpoint 命令上环

urb仍未给回

类驱动对 -EPIPE 的标准回应是发 CLEAR_FEATURE(ENDPOINT_HALT)（清设备侧 stall），usb core 随后调 hcd 的 endpoint_reset——内核发现 toggle 已被第 2 帧的 Reset EP 硬清过（旗标在案），免去 Configure Endpoint D+A 重清。此刻软硬两台状态机同回零位。十个旗标的公共语义一句话：端点不在可运行态，就不催硬件、不收新活、按部就班走命令环。
收拢：xHCI 里"端点的状态"有两份——硬件 EP ctx 五态（§4.8.3）是 xHC 自己的状态机，软件 ep_state 十旗标（xhci.h:672-685）是驱动的簿记；两者通过命令环上的 Reset/Stop/Set TR Dequeue 与事件环上的 Transfer/Command Completion 对话。urb_dequeue（:1849-1860）那张"三态让路、两态秒断"的分派表，就是这套簿记的消费端——读懂它，cancel/超时/halt 交织的并发路径就不再神秘。
