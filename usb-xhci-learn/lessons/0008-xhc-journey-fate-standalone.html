专题 · 一个 TD 该回几个事件？规范对 Transfer Event 的产生只立了三种情况（§4.11.3.1，p222）：① 某个 TRB 完成，且它的 IOC（Interrupt On Completion，DW3 bit5）为 1；② 传输中发生短包，且该 TRB 的 ISP（Interrupt-on-Short Packet，DW3 bit2）为 1；③ TRB 执行中出错。xHC 不保证「每个 TD 一个事件通知」——只有条件满足才写事件。步进器第②段的 :3864-3869（Data·ISP）与 :3910-3915（Status·IOC）就是这两个标志位的设置。

对照实测样本：TD1 要 8 字节、设备足额交 8 字节——ISP 条件未满足，只有 Status 的 IOC 条件满足 → 整个一个事件（EV4，落在 Status TRB 上）。TD2 要 64 字节、设备只有 18 字节——ISP 条件满足 → EV6（Short Packet，残量 46）；Status 照常走完，IOC 再交 EV7。TD3（SET_CONFIG）没有 Data 段，干净走完只回 EV9——事件个数跟着「满足几条条件」走，不跟着 TD 走。

夹在中间的 EV5 不是 Transfer Event，是命令完成事件——核对对象是命令环：事件的 DW0-1 回指它完成的那颗命令 TRB，handle_cmd_completion（xhci-ring.c:1803）拿它与命令环指针核对，匹配后唤醒排队时登记的 xhci_command 等待者（如 xhci_setup_device 里睡着的 wait_for_completion），随后命令环指针前移一格。三类事件三套口径：Transfer → 传输环上的 TD/URB；命令完成 → 命令环上的命令与等待者；端口事件（EV1）→ 没有口径，直接读 PORTSC 状态位。

专题一 · 四种传输各自的结局：错误路径全图

六步主线与 M4.5 实测样本走的都是 happy path（九颗事件全是 Success/Short Packet）。真实总线上会出错——xHCI 把错误约定成两层：完成码 CC（Table 6-91 p507：随事件回报路径带回）与端点状态后果（这个错误会不会让 xHC 侧端点停机）。第二层的判定函数只有一个，值得整段读：

/* xhci-ring.c:2204-2231（xhci_halted_host_endpoint）——哪些 CC 让 xHC 端点 halt */
static bool xhci_halted_host_endpoint(struct xhci_hcd *xhci, struct xhci_ep_ctx *ep_ctx,
				      unsigned int comp_code)
{
	int ep_type = CTX_TO_EP_TYPE(le32_to_cpu(ep_ctx->ep_info2));

	switch (comp_code) {
	case COMP_STALL_ERROR:
		/* on xHCI this always halts, including protocol stall */
		return true;
	case COMP_BABBLE_DETECTED_ERROR:
		/*
		 * The 0.95 spec says a babbling control endpoint is not halted.
		 * The 0.96 spec says it is. Some HW claims to be 0.95
		 * compliant, but it halts the control endpoint anyway.
		 * Check endpoint context if endpoint is halted.
		 */
		if (xhci->hci_version <= 0x95 && ep_type == CTRL_EP)
			return GET_EP_CTX_STATE(ep_ctx) == EP_STATE_HALTED;

		fallthrough;
	case COMP_USB_TRANSACTION_ERROR:
	case COMP_SPLIT_TRANSACTION_ERROR:
		/* these errors halt all non-isochronous endpoints */
		return ep_type != ISOC_IN_EP && ep_type != ISOC_OUT_EP;
	}

	return false;
}

三个要点：① STALL 总是 halt 主机侧端点——包括 ep0 的协议 stall（设备侧 ep0 stall 只是"本请求不支持"，但 xHC 内部状态照样要 Reset Endpoint 清理；设备侧 halt 由类驱动随后发 CLEAR_FEATURE(ENDPOINT_HALT) 清，:2201-2202 注释）；② Babble 在 0.95/0.96 规范间变过卦，内核对声称 0.95 的老硬件改查 EP 上下文实态（:2213-2221，实现≠规范 家族的又一枚）；③ USB Transaction Error / Split Transaction Error halt 一切非等时端点——等时端点天生豁免（§4.10.2.8：等时错误逐帧上报、传输继续，"错一帧不赖整条流"）。另外 USB Transaction Error 在走到这个判定函数之前，xHC 硬件已经按 EP 上下文的错误计数自行重试过若干轮（§4.10.2.3 / §4.10.2.7 Bus Error Counter）——内核看到的是硬件重试穷尽后的最终结果。

📎 §4.10.2.1 Stall Error（线上形态）（p195）

xHCI 1.2（2019） · p195

A STALL PID (USB2) or STALL LMP (USB3) may be returned by a USB function in response to an IN token or after the data phase of an OUT or in response to a PING transaction. The STALL PID indicates that a function is unable to transmit or receive data, or that a control pipe request is not supported.

功能性 stall 的判据在设备侧：收不了/发不了，或控制请求不支持——与协议 stall（ep0 专用）区分。

📎 §4.10.2 Errors（错误必停环）（p195）

xHCI 1.2（2019） · p195

All Transfer Ring error conditions force the state of the associated endpoint to Halted and require system software intervention to recover.

为什么 STALL 之后 urb 不能直接交还：端点已被强制 Halted，必须系统软件（本步进器③-⑥步）出面恢复。

📎 §4.6.8 Reset Endpoint（p128）

xHCI 1.2（2019） · p128

The Reset Endpoint Command is issued by software to recover from a halted condition on an endpoint.

③步写入命令环的那条命令；同页前文：环停时端点被移出调度表、管道门铃被禁、后续包静默丢弃——即②步「必须有人来救」的规范依据。

📎 §4.6.10 Set TR Dequeue Pointer（冲缓存）（p141）

xHCI 1.2（2019） · p141

Invalidate any xHC TDs that may be cached, forcing xHC to fetch Transfer TRBs from memory when the pipe transitions from the Stopped to the Running state.

④⑤步的规范出处：作废 xHC 缓存 TD、强制重新取指；同节还规定——此命令只允许在 Error/Stopped 态执行（⑤步挡住门铃的原因）。

小结：xHCI 里"端点的状态"有两份——硬件 EP ctx 五态（§4.8.3）是 xHC 自己的状态机，软件 ep_state 十个状态位（xhci.h:672-685）是驱动的记录；两者通过命令环上的 Reset/Stop/Set TR Dequeue 与事件环上的 Transfer/Command Completion 交互。urb_dequeue（:1849-1860）那张"三态避让、两态立断"的分派表，就是这套记录的使用处——读懂它，cancel/超时/halt 交织的并发路径就不再神秘。
