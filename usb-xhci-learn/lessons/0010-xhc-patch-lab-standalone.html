xHC 线四课攒了四张图：0006 的零件图（提单字段、环与段）、0007 的运转图（cycle 合同、回绕点、四把钥匙）、0009 的传输剧（六站旅程、事件环消费、两本账）、0008 的命运面（错误路径、ep_state 旗标）。但四张图画的都是"今天的代码长什么样"——今天的代码是二十多年补丁堆出来的，每一处看起来理所当然的写法，背后往往站着一枚修过真实事故的补丁。

读补丁是检验机制理解最锋利的习题：每枚补丁都是一道"哪条合同被谁违反了"的侦探题——出题人是真实的硬件 bug 或并发竞态，答案是主线内核合入的修复。本课是 xHC 线的实验课：五枚补丁，每枚对应一课的机制面，走同一套五步法：① 症状（谁在什么场景炸了，读 commit message 原文）→ ② 案发现场（修复前的代码）→ ③ 用课程模型走根因 → ④ 修复本体（diff）→ ⑤ 回望（基线今天的代码 + 这枚补丁给课程概念钉的钉子）。

"补丁解析"从此是本课程的长驻功能：后续每门新课的机制学到手后，都配一枚同主题的社区补丁走一遍五步法。配套工具链已入库：scripts/assemble_lesson_blocks.py（代码块装配器——本课全部代码块由 git 原文切片装配，零誊抄）＋ scripts/check_lesson_patches.py（补丁块逐字机检器，--selftest 已过）。

双账本代码块（本课立法，后续补丁课沿用）：同一份源码在本课以三种身份出现，靠代码块头与左条颜色区分——裸块（灰底）＝基线 62f4c998b297 逐字摘录（check_lesson_excerpts.py 机检）；@commit 块（紫条）＝补丁前/后某 commit 的文件状态（check_lesson_patches.py 机检）；diff 块（红条）＝补丁本身的逐字切片；灰条 = commit message 原文。usbcore 侧（urb.c/hcd.c）的基线块也走 @62f4c998 账本——摘录机检器的候选文件表目前只覆盖 xhci 与 core/hub.c。所有行号都对各自账本成立，跨账本行号不可互比。

第 1 章 · 对应 0006 零件课：TRB 的四个字段是分四次写的

补丁：576667bad341「xhci: make sure TRB is fully written before giving it to the controller」（Mathias Nyman，2021-01，+2 行）。

① 症状

/* commit message 原文——机制、复现路径与修法 */
A command TRB is 16 bytes (128 bits) long.
Driver writes the command TRB in four 32 bit chunks, with the chunk
containing the cycle bit last. This does however not guarantee that
chunks actually get written in that order.

This was detected in stress testing when canceling URBs with several
connected USB devices.
Two consecutive "Set TR Dequeue pointer" commands got queued right
after each other, and the second one was only partially written when
the controller parsed it, causing the dequeue pointer to be set
to bogus values. This was seen as error messages:

"Mismatch between completed Set TR Deq Ptr command & xHCI internal state"

Solution is to add a write memory barrier before writing the cycle bit.

压力测试里连挂多台设备反复取消 URB，两颗 Set TR Dequeue Pointer 命令背靠背入队，第二颗只写了一半就被 xHC 取走解析，命令环指针被设成垃圾值。

② 案发现场（补丁前）

/* drivers/usb/host/xhci-ring.c:2924-2939 @576667bad341（修复前的 queue_trb——四次普通 store，无任何顺序保证）*/
static void queue_trb(struct xhci_hcd *xhci, struct xhci_ring *ring,
		bool more_trbs_coming,
		u32 field1, u32 field2, u32 field3, u32 field4)
{
	struct xhci_generic_trb *trb;

	trb = &ring->enqueue->generic;
	trb->field[0] = cpu_to_le32(field1);
	trb->field[1] = cpu_to_le32(field2);
	trb->field[2] = cpu_to_le32(field3);
	trb->field[3] = cpu_to_le32(field4);

	trace_xhci_queue_trb(ring, trb);

	inc_enq(xhci, ring, more_trbs_coming);
}

③ 根因（用 0006/0007 的模型走一遍）

0006 教过：一颗 TRB＝16 字节＝4 个 32 位字段（DW0-DW3），cycle 位在 DW3。0007 立过生产者合同：先落数据、再翻 cycle——xHC 只取 cycle 位匹配的 TRB，所以只要 cycle 位最后写，半成品 TRB 对硬件就不可见。queue_trb 确实把 field[3]（含 cycle）排在最后——但那是 C 源码的书写顺序。CPU 与编译器只保证"单线程自己看"的顺序：四个普通 store 之间可以乱序、合并、延迟可见。一旦门铃敲响（0006 的敲铃＝写 doorbell 寄存器），xHC 作为另一个独立设备立刻从主存取指——它完全可能看见 field[3] 已落、前三字段还在路上的窗口。合同说"先落数据再翻 cycle"，代码却没给这条顺序任何硬件保证。

③ 根因（用 0007 的模型走一遍）

0007 立过铁律：硬件取指只认 TRB 自己带的 cycle 位（§4.9.2：cycle 匹配才取）。Endpoint Context 里的 DCS（Dequeue Cycle State）是给软件看的抄本——xHC 本应在端点停下的时刻更新它。VL805 偷懒：halt 时抄本不动。这段代码出场的时机恰是 0008 讲的 STALL 之后：驱动要取消滞留 TD，用 Set TR Dequeue 命令把硬件 dequeue 挪到安全位置，命令里必须报出挪到之处的新 cycle 值。旧代码拿 hw_dequeue & 0x1——正是 EP Context 抄本的最低位——当新 cycle 的起点。抄本陈旧时，算出的新 cycle 一半概率是反的：写进环里的 TRB 全部"cycle 不匹配"，xHC 一颗都不取，端点当场哑掉。走查循环里的 new_cycle ^= 1 是 0007 的回绕点规则：沿途每跨过一颗会翻转 cycle 的 Link TRB 就翻一次——起点错了，沿途翻得再准也全错。

第 3 章 · 对应 0008 命运课：ep_state 旗标的出口纪律

补丁：f1ec7ae6c9f8「xhci: Always restore EP_SOFT_CLEAR_TOGGLE even if ep reset failed」（Ding Hui，2020-08）。

① 症状

/* commit message 原文——clear_halt 撞上非空队列，旗标卡死的完整传导链 */
Some device drivers call libusb_clear_halt when target ep queue
is not empty. (eg. spice client connected to qemu for usb redir)

Before commit f5249461b504 ("xhci: Clear the host side toggle
manually when endpoint is soft reset"), that works well.
But now, we got the error log:

    EP not empty, refuse reset

xhci_endpoint_reset failed and left ep_state's EP_SOFT_CLEAR_TOGGLE
bit still set

So all the subsequent urb sumbits to the ep will fail with the
warn log:

    Can't enqueue URB while manually clearing toggle

We need to clear ep_state EP_SOFT_CLEAR_TOGGLE bit after
xhci_endpoint_reset, even if it failed.

② 案发现场（补丁前）

/* drivers/usb/host/xhci.c:3234-3243 @f1ec7ae6c9f8（修复前的 xhci_endpoint_reset 收尾——清位只挂在成功路径，cleanup 出口只释放命令）*/

	spin_unlock_irqrestore(&xhci->lock, flags);

	wait_for_completion(cfg_cmd->completion);

	ep->ep_state &= ~EP_SOFT_CLEAR_TOGGLE;
	xhci_free_command(xhci, cfg_cmd);
cleanup:
	xhci_free_command(xhci, stop_cmd);

③ 根因（用 0008 的模型走一遍）

0008 拆过 ep_state 十旗标：EP_SOFT_CLEAR_TOGGLE 的职责是闸门——clear_halt 的软件等效操作（host 侧手工摆平 toggle/sequence 位）进行中时，挡住一切新 URB 插进同一个端点。它的完整生命周期是一对配对变迁：入口置位 → 出口清位。置位点在 xhci_endpoint_reset 开头（基线 xhci.c:3386-3389），拒绝点在入队总口（基线 xhci.c:1689-1692，"Can't enqueue URB while manually clearing toggle"）。问题出在出口：xhci_endpoint_reset 有两个出口——成功出口与 cleanup: 错误出口——而清位语句只写在成功出口。队列非空时函数提前跳到 cleanup:，旗标从此无人清：它不对应任何硬件状态，纯粹是软件忘了收闸，端点从此拒绝一切新 URB。置位与清位必须覆盖所有出口——错误路径也是路径，这是 0008"旗标是配对状态变迁"判读的直接推论。

第 4 章 · 对应 0009 传输剧：EV1/EV2 两颗票之间的记账覆盖

补丁：45ba2154d12f「xhci: fix reporting of 0-sized URBs in control endpoint」（Aleksander Morgado，2015-03）。

① 症状

/* commit message 原文——两颗事件的记账规则与坏判据 */
When a control transfer has a short data stage, the xHCI controller generates
two transfer events: a COMP_SHORT_TX event that specifies the untransferred
amount, and a COMP_SUCCESS event. But when the data stage is not short, only the
COMP_SUCCESS event occurs. Therefore, xhci-hcd must set urb->actual_length to
urb->transfer_buffer_length while processing the COMP_SUCCESS event, unless
urb->actual_length was set already by a previous COMP_SHORT_TX event.

The driver checks this by seeing whether urb->actual_length == 0, but this alone
is the wrong test, as it is entirely possible for a short transfer to have an
urb->actual_length = 0.

This patch changes the xhci driver to rely on a new td->urb_length_set flag,
which is set to true when a COMP_SHORT_TX event is received and the URB length
updated at that stage.

urb->actual_length == 0 to halt re-submitting the RX URB in the control

第 5 章 · 桥向 usbcore：kill 与 giveback 的双 CPU 赛跑

补丁：26fbe9772b8c「USB: core: Fix hang in usb_kill_urb by adding memory barriers」（Alan Stern，2022-01，drivers/usb/core/）。这枚不在 xhci 驱动里——它守住的是 0009 ⑥站 giveback 的 usbcore 侧，也是后续 usbcore 深读课的预告片。

① 症状

/* commit message 原文——syzbot 报告 usb_kill_urb 挂死 */
The syzbot fuzzer has identified a bug in which processes hang waiting
for usb_kill_urb() to return.  It turns out the issue is not unlinking
the URB; that works just fine.  Rather, the problem arises when the
wakeup notification that the URB has completed is not received.

② 出题人的推理（commit message 原文，含双 CPU 时间线）

/* commit message 原文——两个 CPU 并发动作的 outline */
The reason is memory-access ordering on SMP systems.  In outline form,
usb_kill_urb() and __usb_hcd_giveback_urb() operating concurrently on
different CPUs perform the following actions:

CPU 0					CPU 1
----------------------------		---------------------------------
usb_kill_urb():				__usb_hcd_giveback_urb():
  ...					  ...
  atomic_inc(&urb->reject);		  atomic_dec(&urb->use_count);
  ...					  ...
  wait_event(usb_kill_urb_queue,
	atomic_read(&urb->use_count) == 0);
					  if (atomic_read(&urb->reject))
						wake_up(&usb_kill_urb_queue);
/* commit message 原文——SB（Store Buffering）模式的判读 */
Confining your attention to urb->reject and urb->use_count, you can
see that the overall pattern of accesses on CPU 0 is:

	write urb->reject, then read urb->use_count;

whereas the overall pattern of accesses on CPU 1 is:

	write urb->use_count, then read urb->reject.

③ 根因（用 0009 的模型走一遍）

0009 ⑥站给过结论：giveback 之后 urb 交还 usbcore，驱动回调 urb->complete。这枚补丁把镜头拉近到 giveback 收尾与 usb_kill_urb 的并发交汇点：kill 侧 atomic_inc(reject) 后等 use_count == 0；giveback 侧 atomic_dec(use_count) 后看见 reject != 0 就叫醒等待者。注意两边的访问次序——CPU0 先写 reject 再读 use_count，CPU1 先写 use_count 再读 reject，即内存模型里经典的 SB（Store Buffering）模式：双方各自"写自己的变量、读对方的变量"。第 1 章刚讲过：无屏障时 store 对其他 CPU 的可见顺序不受保证，读可以越过自己的写先执行——于是两边可能同时读到旧值：kill 看见 use_count 还是 1（继续睡），giveback 看见 reject 还是 0（不叫醒）。没人错的逻辑，挂死的系统——每个原子操作自身都是原子的，坏的是两个原子操作之间的次序。修法：四个对称位置各插一道 smp_mb__after_atomic() 全屏障（基线在场：urb.c:714、:761；hcd.c:1558、:1667），并把配对关系写进注释。

void usb_kill_urb(struct urb *urb)

	if (!(urb && urb->dev && urb->ep))
		return;

}
