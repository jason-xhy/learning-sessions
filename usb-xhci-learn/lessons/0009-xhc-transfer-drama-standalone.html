整体定位（环会转了，本课看一次传输怎么走完全程）

上一课（0007 环的运转）把环的机械面讲清：cycle 合同、回绕点、四个控制位联动——那是环怎么转。本课换镜头看一件传输怎么走：一个 USB 键盘刚插上，usbcore 发出第一枚 urb（GET_DESCRIPTOR 读设备描述符），这次传输从打包（TRB 化）、写环、上线、DMA 搬运到事件通知的全过程，由三方共同参与——软件（xhci-hcd 驱动）、xHC 控制器、设备固件。主角是三个容易卡住的问题：控制传输 2 颗 TRB 的 chain 在哪设（答案反直觉：全程零 chain）、一个控制传输到底几件 TD（两套口径）、Status 段为什么砍不得（三阶段分工）；外加一个必须讲清的点：xHC 怎么通知驱动——事件是完成通知，不是取数据凭据。第 6 章另收两个问题：ZLP 是什么（零长包的两种用途）、一次中断两颗事件谁先谁后（FIFO 消费与 process_ctrl_td 分岔）。六站全景图全程适用，但现在每站都要问一句：这一站谁在动？

三个角色的分工（本课全程适用）：软件（xhci-hcd 驱动）——TRB 生产者（传输环上写 TRB）、事件消费者；xHC 控制器——TRB 消费者（沿环读 TRB）、线上事务的翻译官与搬运者（收包即 DMA 直写）、事件生产者（事件环上写事件通知）；设备固件——线上对端，只看得见令牌与包（token/数据包/握手），环对它完全不可见——环住在只有软件与 xHC 能读写的共享内存里（0007 开篇约定，本课动画每帧遵守）。线上通道画在 xHC 与设备之间：令牌永远主机发，载荷生产者每个阶段换手。

第 1 帧布景——TRB 还没贴：三视角开场，urb 到门口

本帧只看「TRB 还没贴」：环空开局（"空"＝cyc 不匹配，两侧轮次=1，没有任何标志槽）。usbcore 的第一枚 urb 已到软件侧门口：键盘刚插上，枚举第一步＝读设备描述符。xHC 侧扫描停驻等门铃；设备侧复位毕、EP0 待命。注意 xHC 视角的侧注——SET_ADDRESS 不走这颗环，xHCI 把它挪到了命令环（Address Device 命令，BSR=0，xHC 自己上线，§4.6.5），端点环上只看得到 GET_DESCRIPTOR / SET_CONFIGURATION 这类（0008 的 M4.5 标本会逐帧重演这一段）。

第 2 帧软件视角 · 写环——零 chain 的 TD1 落槽（xHC 看不见半成品）

本帧只看环上三颗槽：整颗 TD 没有一个 chain=1。Setup 槽连 chain 位都不存在——DW3 bit4:1 是 RsvdZ（Table 6-26），规范没给它留位置；Data/Status 的 chain=0 原样。这不是漏设：bulk 的 Normal 流颗数任意，chain 是唯一分件约定；控制的 TD 边界写在类型语法里——Setup 的 TRT=IN（贴码 :3847-3855）就是「下一段是 Data IN」的预告。发布纪律与 bulk 完全同一套：首 TRB 反极性压着（:3844-3845——start_cycle=1 时什么都不写＝保持 0），trailing 现写现发（Status 直接 | ep_ring->cycle_state，:3915）；queue_trb 的 more_trbs_coming 参数 Setup/Data 传 true、Status 传 false（:3857/:3893/:3910）。xHC 侧看得见环却取不走——cyc 不匹配是物理止步；设备侧无戏份：这一阶段发生在它完全看不见的共享内存里。

第 3 帧xHC 视角 · 发布与 Setup 阶段——写门铃后取 TRB，类型带路，设备准备数据

本帧只看 xHC 被什么推着走：发布＝软件侧先 wmb、再翻首 TRB 的 cyc 0→1，门铃敲响。xHC 从 ▼ 顺序扫描——cyc 匹配进环，之后每一步都是类型在带路：Setup 类型→读 TRT=IN→知道下一颗是 Data 段。线上第一笔事务开始：SETUP 令牌＋8B 包体上线（包体就是 Setup 槽上 IDT 内联的那 8 字节：80 06 00 01 00 00 40 00）。设备侧第一次出场——规范级行为只有两步：收令牌、按请求准备数据（18B 设备描述符待发）。软件侧已交出议程，闲等回调。注意线上方向：令牌永远主机发——总线调度权在主机，设备永远不能先开口（第 5 章分工图约定）。

第 4 帧设备视角 · Data 阶段——设备是载荷生产者，xHC 收包即 DMA 直写

本帧看的是全剧换手：Data 阶段载荷生产者＝设备。线上三步：xHC 发 IN 令牌 → 设备回 18B 数据包（描述符只有 18B，64−18=46 残量——短包，ISP 即刻生效）→ xHC 校验 CRC、回 ACK。然后是最容易被忽略的一笔：xHC 把 18B 用 DMA 直写进 Data TRB 的 Buffer Pointer 所指内存——那个地址是软件侧入队时就写好的合同（帧 2 的「只写缓冲地址」）。看软件侧的缓冲区盒：数据此刻已经在驱动内存里了，但通知还没发——ISP 短包事件 EV1 刚落事件环，中断还没拉，软件对这一切一无所知。这一拍的完整约定（事件=完成通知）是第 4 章的主角。设备发完悬在「等主机确认」——Status 阶段之前，交易还不算成。

第 5 帧收官 · Status 阶段与完成通知——确认、产生事件、拉中断、还 urb

本帧把 Status 阶段与通知链一次演完：xHC 取 Status TRB，线上 OUT 零长包＝主机的收尾确认（数据段 IN ⇒ status 事务走 OUT，:3904-3909 的 DIR 翻转）；设备回 ACK——「本次传输完成」只有这一阶段能说。收尾后 xHC 转身当事件生产者：写 EV2 Success（事件字段 TRB 回指 Status 槽＝对上 td->end_trb 末 TRB 记录，:3901 排队时记下的）→ 翻事件 cycle → 拉 MSI-X 中断（回程不写门铃：方向反转，中断拉软件）。软件侧被打断：xhci_irq → 沿 ERST 消费 → EV1 记录 actual_length=18、EV2 对末 TRB 记录收尾 → xhci_giveback_urb_in_irq（:807）把 urb 还给 usbcore。主环三颗变旧值残留——消费不擦、覆写即回收。hub 线 0002 讲的「描述符长度以实际短包为准」，在事件环上是两颗事件两笔记录（短包双事件，0008 M4.5 标本同款）。「2 颗」的一生：下一次 SET_CONFIGURATION（setup 包 00 09 01 00 00 00 00 00，wLength=0）＝Setup 的 TRT=0 预告「没有 Data 段」，xHC 读完 Setup 直接跳 Status 收尾——2 颗、零绳、TD 边界照样清晰（num_trbs 注释原话「1 TRB for setup, 1 for status」，:3813-3814；同一台钟上的同构两拍版）。至此键盘 configured：之后每次按键＝interrupt IN 端点上 1 颗 TRB 的小 TD（单颗即一件，chain 也用不上——它真正的主场是 bulk 大件数据，0007 联动动画）。

问三小结：控制传输的 TD 边界写在类型语法里，不写在 chain 位里——Setup 段连这个位都没有（DW3 bit4:1=RsvdZ，Table 6-26）；TRT 预告段结构、Status 类型收尾、IOC 产生事件；chain 的主场在 bulk/interrupt 的 Normal 流（与 isoc）。跨过回绕点时 bulk 的 Link 被 chain=1 续上、控制的 Link 反被清 0——续链由类型扛，ETRON 怕硬件扛不住才垫 No-Op。三视角各演一遍同一份合同：软件写环（反极性压着 → wmb → giveback 翻 cycle → 门铃）↔ xHC 消费（cyc 校验 → 类型推进 → 上线执行）↔ 设备听令（收令牌 → 准备数据/发送/确认）；到了事件环上，软件与 xHC 整套合同原样对调（xHC 写、软件读）。钟序证据在第 3 章。

第 5 章 三阶段分工与两套口径

读者问四（原话）：「你的理解是不是有问题？一个控制传输有3个阶段setup\data\status，分别对应3个 TD，也就是一个trb就是一个td」——并自引规范原文（§6.4.1.2）："Control transfers require two or three TDs to define them: a Setup Stage TD followed by an Status Stage TD, if a data stage is required for the transfer an optional Data Stage TD will reside between the Setup Stage and Status Stage TDs. 问四问五小结：TD 是两套口径——规范按阶段记 2-3 件（Setup 恒单颗是法条、Data 在 Linux 恒单颗是选择），内核按 URB 记 1 件、末 TRB 记录指 Status；三阶段是「问 → 答 → 确认」——令牌恒主机发、载荷生产者每个阶段换手两次，确认不是第三种数据，是「收尾」动作本身，软件侧一切「完成」信号（IOC、事件、中断、回调）都记在确认那颗 TRB 名下。方向规则：Status 恒与 Data 反向（:3904-3909 的 if/else 在翻的就是它）；零数据段控制写则 Status＝IN。

第 6 章 ZLP 的两种用途·一次中断两颗事件（读者提问）

读者问六（原话）：「ZLP是什么？」——帧 5 挂出「确认 ZLP」标签以来，第一次被追问这个词本身。

先给字面：ZLP＝Zero-Length Packet，零长度包——一个真实存在的 USB 数据包：有令牌、有 DATA0/DATA1 的 PID、走完整的 CRC 与握手，只是数据载荷恰好 0 字节。它不是「没有发包」，而是「发了一个空包」——空本身就是信息。为什么「不发数据」也要发一个包？USB 事务的校验与确认（CRC、握手、数据翻转）全部挂在包上；零长包让「收尾」也走完整的确认流程，两侧的数据翻转序列保持一致。

ZLP 在协议里有两个用途，一个本课天天在用，一个留给 bulk 主场：

用途场景谁发 ZLP买到什么
① Status 阶段的载荷

问六问七小结：ZLP＝恰好 0 字节的正式数据包——控制传输里它是 Status 阶段的载荷（数据段 IN ⇒ 主机 OUT 确认、无数据段 ⇒ 设备 IN 确认生效），bulk 里它是总长恰为 wMaxPacketSize 整数倍时的整包结尾标记；短包是「比预告少」，两者是不同的边界信号。一次中断两颗事件：先 EV1 后 EV2＝事件环 FIFO＋单循环顺序消费，分岔在 process_ctrl_td——EV1 记录不放行（urb_length_set＋actual_length=18），EV2 对末 TRB 记录收尾（finish_td → 主环 dequeue 落末 TRB 记录＋1 → giveback）；两笔记录只在短包出现（ISP 产生事件），满包只有一颗 IOC 收尾事件。
