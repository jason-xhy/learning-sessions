整体定位（环会转了，本课把一件货交给三个演员演完）

上一课（0007 环的运转）把环的机械面钉死：cycle 合同、接缝、四把钥匙联动——那是环怎么转。本课换镜头看货怎么走：一个 USB 键盘刚插上，usbcore 发出第一枚 urb（GET_DESCRIPTOR 读设备描述符），这桩交易从打包、贴单、上线、搬货到还账的全过程，由三个演员合演——软件（xhci-hcd 驱动）、xHC 控制器、设备固件。主角是读者 2026-10-10 的三个追问：控制传输 2 颗 TRB 的 chain 在哪设（答案反直觉：全程零 chain）、一个控制传输到底几件 TD（两本账）、Status 段为什么砍不得（三幕柜台）；外加一个本课新立的法：xHC 怎么通知驱动——事件是完税回执，不是取货单。六站全景图全程适用，但现在每站都要问一句：这一站谁在动？

三演员立法（本课全程有效）：软件（xhci-hcd 驱动）——贴单生产者（传输环上写 TRB）、事件消费者；xHC 控制器——取件消费者（沿环读 TRB）、线上事务的翻译官与搬运工（收包即 DMA 直写）、事件生产者（事件环上写回执）；设备固件——线上对端，只看得见令牌与包（token/数据包/握手），环对它完全不可见——环是软件与 xHC 的共享内存私聊（0007 开篇立法，本课动画每帧遵守）。线上通道画在 xHC 与设备之间：令牌永远主机发，载荷生产者每幕换手。

三层看一眼就够（细节在 0006）：urb 是 usbcore 的货币，TRB 是环上的 16 字节提单，段与环是货架几何。Data 段提单上没有货，只有地址——64B 读缓冲的 DMA 地址写进 Buffer Pointer，这张"空地址合同"正是第 4 章 DMA 直写的伏笔：xHC 收到设备的数据包后，直接按这个地址把货写进驱动内存。

第 2 章 键盘枚举·一部动画（三泳道合演，读者实问）

读者问三（2026-10-10 原话复述）：「一次控制传输消耗 2 个 trb，但没看到代码中 chain bit 是如何设置的。」并附一个请求：以 USB 键盘枚举为例画一部动画——生产者、消费者两个角度分别怎么读写 cycle bit / Link TRB / TC / chain bit，以及 urb / trb / td / segment / ring 之间的关系。两件事一个答案：先补码（控制路径的 chain 立法真相），再上动画（软件 / xHC / 设备三条泳道同台）。

三段全程零 chain。规范层把这件事立法得很彻底，三层递进：

① Setup 段根本没这个位：Table 6-26（1.2 p469 / 1.2b p430）的 DW3 位图——bit 4:1 是 RsvdZ。Normal TRB 的 bit4 住着 chain，Setup 段这里是一块「不许施工」的空地：chain 想设也没位可设。bit 17:16 住的是 TRT（Transfer Type：0=无数据段 / 2=OUT / 3=IN）——预告「下一颗是不是 Data 段」的就是它。
↓
② 类型即分件：§4.11.2.2（p211）——Setup / Data / Status 三种段 TRB 与 USB 控制传输的三个阶段 1:1 映射。TD 结构是一套封闭语法：Setup(TRT) →（可选 Data）→ Status 收口；§6.4.1.2 开头 Note（p468）：IOC 只应设在 Status 段。xHC 被类型推着走，不需要绳。
↓

第 1 帧布景——货还没贴：三泳道开场，urb 到门口

本帧只看「货还没贴」：环空开局（"空"＝cyc 不匹配，两侧轮次=1，没有任何标志槽）。usbcore 的第一枚 urb 已到软件泳道门口：键盘刚插上，枚举第一步＝读设备描述符。xHC 泳道扫描停驻等门铃；设备泳道复位毕、EP0 待命。注意 xHC 泳道侧注——SET_ADDRESS 不走这颗环，xHCI 把它挪到了命令环（Address Device 命令，BSR=0，xHC 自己上线，§4.6.5），端点环上只看得到 GET_DESCRIPTOR / SET_CONFIGURATION 这类（0008 的 M4.5 标本会逐帧重演这一段）。

第 2 帧软件泳道 · 贴单——零 chain 的 TD1 落槽（xHC 看不见半成品）

本帧只看环上三颗槽：整颗 TD 没有一个 chain=1。Setup 槽连 chain 位都不存在——DW3 bit4:1 是 RsvdZ（Table 6-26），规范没给它留位置；Data/Status 的 chain=0 原样。这不是漏设：bulk 的 Normal 流颗数任意，chain 是唯一分件立法；控制的件界写在类型语法里——Setup 的 TRT=IN（贴码 :3847-3855）就是「下一段是 Data IN」的预告。发布纪律与 bulk 完全同一套：首 TRB 反极性压着（:3844-3845——start_cycle=1 时什么都不写＝保持 0），trailing 现写现发（Status 直接 | ep_ring->cycle_state，:3915）；queue_trb 的 more_trbs_coming 参数 Setup/Data 传 true、Status 传 false（:3857/:3893/:3910）。xHC 泳道看得见环却取不走——cyc 不匹配是物理止步；设备泳道无戏份：这一幕发生在它完全看不见的共享内存里。

第 3 帧xHC 泳道 · 发布与 Setup 幕——敲铃取件，类型带路，设备备货

本帧只看 xHC 被什么推着走：发布＝软件泳道 wmb 后翻首 TRB 的 cyc 0→1，门铃敲响。xHC 从 ▼ 顺序扫描——cyc 匹配进环，之后每一步都是类型在带路：Setup 类型→读 TRT=IN→知道下一颗是 Data 段。线上第一笔事务开演：SETUP 令牌＋8B 包体上线（包体就是 Setup 槽上 IDT 内联的那 8 字节：80 06 00 01 00 00 40 00）。设备泳道第一次出场——规范级行为只有两步：收令牌、按请求备货（18B 设备描述符待发）。软件泳道已交出议程，闲等回调。注意线上方向：令牌永远主机发——总线调度权在主机，设备永远不能先开口（第 5 章柜台图立法）。

第 4 帧设备泳道 · Data 幕——设备是载荷生产者，xHC 收包即 DMA 直写

本帧是全剧换手的一幕：Data 幕载荷生产者＝设备。线上三步：xHC 发 IN 令牌 → 设备回 18B 数据包（描述符只有 18B，64−18=46 残量——短包，ISP 即刻生效）→ xHC 校验 CRC、回 ACK。然后是最容易被忽略的一笔：xHC 把 18B 用 DMA 直写进 Data TRB 的 Buffer Pointer 所指内存——那个地址是软件泳道贴单时就写好的合同（帧 2 的「只写缓冲地址」）。看软件泳道的缓冲区盒：数据此刻已经在驱动内存里了，但通知还没发——ISP 短包事件 EV1 刚落事件环，中断还没拉，软件对这一切一无所知。这一拍的完整立法（事件=完税回执）是第 4 章的主角。设备发完悬在「等主机签收」——Status 幕之前，交易还不算成。

第 5 帧收官 · Status 幕与完税回执——签收、出票、拉中断、还 urb

本帧把 Status 幕与回执链一次演完：xHC 取 Status TRB，线上 OUT 零长包＝主机的签收回执（数据段 IN ⇒ status 事务走 OUT，:3904-3909 的 DIR 翻转）；设备回 ACK——「这桩成了」只有这幕能说。收口后 xHC 转身当事件生产者：写 EV2 Success（票面 TRB 回指 Status 槽＝对上 td->end_trb 票根，:3901 排队时记下的）→ 翻事件 cycle → 拉 MSI-X 中断（回程不敲铃：方向反转，中断拉软件）。软件泳道被打断：xhci_irq → 沿 ERST 消费 → EV1 记账 actual_length=18、EV2 对票根收口 → xhci_giveback_urb_in_irq（:807）把 urb 还给 usbcore。主环三颗变残影——消费不擦、覆写即回收。hub 线 0002 讲的「描述符长度以实际短包为准」，在事件环上是两颗事件两笔记账（短包双事件，0008 M4.5 标本同款）。「2 颗」的一生：下一桩 SET_CONFIGURATION（setup 包 00 09 01 00 00 00 00 00，wLength=0）＝Setup 的 TRT=0 预告「没有 Data 段」，xHC 读完 Setup 直接跳 Status 收口——2 颗、零绳、件界照样清晰（num_trbs 注释原话「1 TRB for setup, 1 for status」，:3813-3814；同一台钟上的同构两拍版）。至此键盘 configured：之后每次按键＝interrupt IN 端点上 1 颗 TRB 的小 TD（单颗即一件，chain 也用不上——它真正的主场是 bulk 大件货，0007 联动动画）。

问三收拢：控制传输的件界写在类型语法里，不写在 chain 位里——Setup 段连这个位都没有（DW3 bit4:1=RsvdZ，Table 6-26）；TRT 预告段结构、Status 类型收口、IOC 出票；chain 的主场在 bulk/interrupt 的 Normal 流（与 isoc）。跨缝时 bulk 的 Link 被 chain=1 缝上、控制的 Link 反被清 0——续链由类型扛，ETRON 怕硬件扛不住才垫 No-Op。三泳道各演一遍同一份合同：软件贴单（反极性压着 → wmb → giveback 翻 cycle → 门铃）↔ xHC 取件（cyc 校验 → 类型推进 → 上线演戏）↔ 设备听令（收令牌 → 备货/发货/签收）；到了事件环上，软件与 xHC 整套合同原样对调（xHC 写、软件读）。钟序证据在第 3 章。

第 4 章 Data 段谁生产·事件怎么通知（本课新立法）

帧 4 与 T7 留下的问题：软件泳道拿到 18B 描述符，靠的不是自己去取——那通知链到底怎么走？先把事实链钉死（GET_DESCRIPTOR 控制读，三方分工）：

① Data 段线上：设备＝载荷生产者，xHC＝搬运工。xHC 发 IN 令牌 → 设备回数据包 → xHC 校验 CRC、回 ACK → xHC 把数据 DMA 直写进 Data Stage TRB 的 Buffer Pointer 所指内存（驱动建 TRB 时填好的 urb 缓冲区 DMA 地址）。驱动从头到尾不接触"包"——它只在合同里写了一个空内存地址。
↓
② 通知：xHC 转身＝事件生产者。整桩三段走完（或 TRB 带 IOC 位，§4.10.4）→ xHC 在事件环写 Transfer Event TRB（Table 6-37，§6.4.2.1 p477）——票面三字段：完成码 CC / 传输字节数（残量）/ 回指完成的传输 TRB 地址（"一件一票·票面回指"机制）→ 翻事件 cycle → 拉中断（MSI-X 主流——§4.17 Interrupters 及其 MSI-X 实现注记；MSI/INTx 备胎）。

第 5 章 三幕柜台与两本账（读者实问）

读者问四（2026-10-10 原话复述）：「你的理解是不是有问题？一个控制传输有3个阶段setup\data\status，分别对应3个TD，也就是一个trb就是一个td」——并自引规范原文（§6.4.1.2）："Control transfers require two or three TDs to define them: a Setup Stage TD followed by an Status Stage TD, if a data stage is required for the transfer an optional Data Stage TD will reside between the Setup Stage and Status Stage TDs. This section defines the TRBs that comprise the respective TDs. Refer to section 4.11.2.2 for more information on xHCI control transfers."

先裁定：你引的原文一字不差（§6.4.1.2，p467 起），「每阶段一件 TD」的读法对；要修的只有半句——「一个 TRB 就是一个 TD」不是定义，是三层巧合的叠加。而这半句误读的根子不在读者，在课件："TD"这个词在规范和 Linux 内核里是同名不同粒度的两本账，第 1 章五层包裹只立了内核那本（「TD＝驱动侧对账单位」），没把两本账并排挑明——本章补上这笔账。

为什么内核按 URB 记？对账面只需要一件：一个 urb 一个完成回调、一张票根（帧 5「一件一票」）；而控制传输那张收口票恒出自 Status 段——IOC 只许设在 Status（§6.4.1.2 Note p468；内核 :3915 的 TRB_IOC），整件货的账记在第三幕名下。你拿规范账本（3 件）去数内核的件（1 件），得出「1≠3」的假矛盾——两本账都没记错，错在课件没挑明撞名。

离场即破的提醒：bulk 传输一个 TD 串几十颗 TRB 是常态——chain 剪刀的主场（0007 钻点三）。正确说法是：规范按阶段记件；控制传输的每件通常恰一颗 TRB（Setup 恒如此、Data 在 Linux 恒如此）；内核再把这几件打成自己的一件对账。这也再次解释第 2 章的立法：这 2-3 件 TD 之间没有 chain 胶水——件界写在类型语法里。

读者问五（2026-10-10 原话复述）：「再普及一下setup\data\status段的功能以及对应的生产者和消费者，比如GET_DESCRIPTOR，软件为什么要发起setup\data\status这3段trb？如果只是获取描述符，那么一个setup trb、一个data trb不就够了吗？」

先看这桩交易在线上怎么演——令牌永远主机发（总线调度权在主机，设备永远不能先开口），但载荷的生产者每幕换一次手：

「只是拿个描述符，两颗不就够了吗？」——不够，四条理由：

① TRB 是议程行，不是数据本身。Data TRB 回答「搬什么、搬多少」；Status TRB 回答「怎么办结」——它长度 0、不带一个字节的货，却必须占一行议程，xHC 才有动作可演（发 OUT 零长包、收 ACK）。两颗 TRB＝议程只排到第二幕。
↓
② 三幕是 USB 总线协议的法定结构（USB 2.0 §8.5）——xHCI §4.11.2.2 只是把三阶段 1:1 翻成三种 TRB，内核不是多要一颗、是照单排班：排 Status 那行的注释自己引着规范（:3904）"see Table 7 and sections 4.11.2.2 and 6.4.1.2.3"。
↓
③ 最后一包数据 ≠ 交易完成。短包票（CC=13，残量 46）只是中途报账——记下实际长度 18，但不放行 urb（process_ctrl_td 的 "Waiting for status stage event"，:2386）；IOC 只许设在 Status（§6.4.1.2 Note p468＝内核 :3915）——完成中断的定义权本来就在第三幕。
↓
④ 设备要「关门」信号，「成了」这句话只有这幕能说。搬完货设备 EP0 状态机悬在「等主机签收」，OUT 零长包就是主机的回执；STALL 拒绝可以早到 Data 幕，但成功宣言只能晚到 Status 幕。SET_CONFIGURATION 更极端：没有 Data 幕（2 颗的一生，帧 5），Status 的 IN 零长包＝设备「配置已生效」的唯一一句。

反证：真只排两颗——xHC 控制序列停在半空（类型语法没等到 Status 收口），完成事件出不来，设备悬在 Data 幕尾；下一个 setup 能强行重开，但协议管那叫中止上一笔，不叫完成。旁证你已经见过（帧 1 侧注）：SET_ADDRESS 连 EP0 环都不上——走命令环的 Address Device 命令，xHC 自己在线上把三幕演完。同一个道理换个舞台：线上三幕逃不掉，议程写在哪个环上可以换。

问四问五收拢：TD 是两本账——规范按阶段记 2-3 件（Setup 恒单颗是法条、Data 在 Linux 恒单颗是选择），内核按 URB 记 1 件、票根指 Status；三幕是「问 → 答 → 签收」——令牌恒主机发、载荷生产者每幕换手两次，签收不是第三种数据，是「办结」动作本身，软件侧一切「完成」信号（IOC、事件、中断、回调）都记在签收那颗 TRB 名下。方向口诀：Status 恒与 Data 反向（:3904-3909 的 if/else 在翻的就是它）；零数据段控制写则 Status＝IN。

回到整体（happy path 的三方机理收官）

本课把 0007 的环装上了货：六站全景＋五层包裹＋零 chain 立法＋键盘枚举三泳道动画＋十二拍钟序＋事件通知链＋两本账＋三幕柜台——一件控制传输的 happy path 从此每一拍都有三方各自的解释：软件贴单与收账、xHC 取件与搬运与出票、设备听令与发货与签收。但到这里为止事件全是 Success/Short Packet，端点从不出错。下一课（0008 旅程实战与命运）看真实标本与出错的命运：用我们亲手实现的 M4.5 引擎把 set_address 全握手的九条事件逐帧跑给你看（数字全部实测，含短包双事件与环回绕轮转——正是本课帧 4/帧 5 两颗事件的标本级重演）；拆开错误路径全图（CC 判决表→四种传输各自的命运）；拆开ep_state 十旗标——STALL 到恢复的完整软硬协同时序。hub 线视角的呼应：0002 课你看到的是"主机复位端口、设备拿到地址"；本课之后你知道那背后是 PORT 事件、命令环上的两段式 BSR、事件环上的九颗回执。xHC 线地图钉：0006 认零件 → 0007 环机制 → 0009（本课）一场传输的三视角剧 → 0008 实战与命运。
